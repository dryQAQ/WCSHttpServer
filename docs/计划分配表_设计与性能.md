## 一、它解决什么问题

### 1.1 客户口径（本模块要落地的不变量）

1. **每个格口都有"对应这个产品的数量"**：同一个 SKU（产品）可以同时计划到
   **「正常分拣（分类）格口」** 与 **「发货格口」**，两个格口**各有一份数量**；
   落格必须**按各格口的数量**分过去，而不是全部投第一个格口。
   - 例：`106101134113101 → 22034(正常分拣):1件 + 22048(发货):3件` ⇒ 4 件里 1 件进 034、3 件进 048。
   - 66 号是**物理异常口**，不属于任何产品的计划，只收"超计划件"。
2. **人工失误/同时两件在线导致"箱内实落 > 计划"必须被拦住**：
   已落格 + 在途认领 ≥ 计划件数时，后续件一律改投异常口（66）。

### 1.2 改造前的缺陷（已修复，逐一对应到代码位置）

| # | 缺陷 | 位置 | 现场后果 |
|---|---|---|---|
| D1 | 计划件数用"SKU 计划总数"兜底 | `planQtyOfGrid()`、`clampFullboxQtyToPlan()` | 多格口 SKU（34 计划1 + 48 计划3，总数4）在 034 放 4 件都不裁不预警 → **超计划失守**（人工多投没被拦住的直接原因） |
| D2 | 落库把 SKU 总数写进每格口计划 | `buildWaveItems()` | `return_wave_item` 无法回答"这个格口计划几件"，波次恢复后计划被污染 → **追溯链断裂** |
| D3 | 同格口多行"取大者" | `ParseWorker.cpp` | 同一波次恢复前后计划数不一致 → 不可重现 |
| D4 | 选格不预留额度（先查已落数、再另行登记） | `PlcManager.cpp` | 同时两件在线时两件都判"未满额" → 都发同一格口 → 实落超计划 |
| D5 | 计划格口禁用/锁格时计划直接流失 | `PlcManager.cpp` | 计划 3 件只落 1 件，其余全进 66 |
| D6 | 候选集（映射串）与计划表两套真相 | `PlcManager.cpp` | 不一致时静默退回"取首个格口"老逻辑 |
| D7 | 无波次归属 | `DoubleBuffer` 上的计划表 | 旧波次计划可能作用于新波次前几件 |
| D8 | 66 号件被当"落错格" | `isGridInPlanOf()` | 追溯语义错误，误导现场排查 |
| D9 | 异常件定位信息不足 | `exception_record` 无 `boxcode` | 人工清出时不知道在哪个箱（现由查询侧关联 `sorting_records.boxcode` 解决） |

## 二、算法设计：把"每次现算"改成"一次性编译"

### 2.1 数据结构（`PlanAllocTable.h`）

**编译期一次性生成（运行期只读）**

| 结构 | 内容 | 大小 |
|---|---|---|
| `PlanCell` | `grid` / `gridType` / `planQty`，按 SKU 连续排布 | 8 B × 计划单元 |
| `SkuPlan` | `planTotal` / `idxFirst` / `idxCount` / `cursorFrom` / `skuRemain` / `gridOff[67]` | ≈ 96 B × SKU |
| `SkuPlan::gridOff` | **本 SKU 的**「格口号 → 计划下标」小表（-1=不在计划内） | 含在上面 |

**运行期可变（只存"活"的）**

| 结构 | 内容 | 大小 |
|---|---|---|
| `CellQuota` | `landed` / `reserv` / `remain` | 12 B × 计划单元 |
| `ClaimRef`（在 `m_claims`：EPC→认领） | `skuIdx` / `planIdx` / `seq` / `atMs` | 只装"在途"，落格/释放/超时即 erase |

### 2.2 额度语义（★最容易写错的地方，务必先读这段）

```
remain = planQty − landed − reserv          （未被占用的额度）

认领 claim          : reserv+1 → remain−1     （占用额度）
落格 commitOnLanded : landed+1 且 reserv−1    → remain 不变（在途转已落，额度已被占用）
释放 release        : reserv−1 → remain+1     （真正归还：下发失败 / 认领超时）
```

> **踩坑记录（离线仿真已复现）**：若把"落格时释放认领"当成"归还额度"
> （即落格后 remain 又 +1），同一格口会被**反复选满**，超计划彻底失守。
> 因此额度写操作被收敛成三个函数：`applyClaim` / `applyCommit` / `applyRelease`，
> 禁止在别处直接改 `landed`/`reserv`/`remain`。
>
> 另：**无认领落格**（人工硬塞、或认领已被超时释放）走 `applyCommitUnclaimed`，
> 只加 `landed` 并重算余量（余量可能为负）——这是"账实优先"路径，
> 由不变量①告警＋异常表留痕，**绝不因认领异常而丢计数**。

### 2.3 复杂度

| 操作 | 实现 | 复杂度 |
|---|---|---|
| 选格 `claim` | 1 次 SKU 哈希 + 按 `idxFirst..+idxCount` 扫（带游标，命中即停） | O(G)，G=该 SKU 计划格口数（通常 1~3） |
| 是否全满 | 读 `skuRemain`（每 SKU 一个计数器） | **O(1)**（不再遍历推导） |
| 落格 `commitOnLanded` | 1 次 SKU 哈希 + 1 次 `gridOff` 下标定位 | **O(1)** |
| 释放 `release` | 1 次 `m_claims` 哈希 | **O(1)** |
| 不变量巡检 `audit` | 全表遍历 | O(计划单元)，仅每 30s 一次 |

### 2.4 空间账（单波次 5 万件 / 2 万 SKU / 平均 2 个计划格口 ≈ 4 万计划单元）

| 项 | 空间 |
|---|---|
| `m_cells`（不可变计划） | ≈ 0.32 MB |
| `m_quota`（可变额度） | ≈ 0.48 MB |
| `m_skus`（编译结果，含 `gridOff[67]`） | ≈ 1.9 MB |
| `m_skuIndex`（SKU→下标） | ≈ 1.0 MB |
| `m_claims`（在途，上限 `allocMaxInflight`=2000） | ≈ 0.10 MB |
| **合计** | **≈ 3.8 MB / 波次，峰值 < 6 MB** |

换来的是：每件选格由「1 次哈希 + G 次 QMap 查找 + G 次比较 + 字符串 key 构造」
降到「1 次哈希 + 数组扫描 + 3 次整数加减」。

### 2.5 确定性（可追溯的前提）

格口顺序在**编译期按格口号升序固化**（`build()` 内 `std::sort`）。
因此同一份 H4 计划，**items 在下发报文里的顺序不同，逐件分配结果完全一致**——
这是"同一波次事后可完整重现"的基础（改造前候选顺序取自 `gridNum` 逗号串的解析顺序，不可重现）。

## 三、运行期流程

```
H4 下发
  └─ ParseWorker（低优先级线程）
       · 同格口多行 **累加** → planQtyPerGrid；按格口保存 gridTypePerGrid
       · 整理出「SKU → [(格口,类型,件数)]」随 waveParsed 信号交给主线程
  └─ HttpServer::buildPlanAllocTable（★ 主线程，波次内唯一一次）
       · 剔除计划里的异常口(66)
       · PlanAllocTable::build() 固化顺序 → m_allocValid = true
       · 日志：[计划分配表] 构建 order=… SKU=… 计划单元=… 计划件数合计=…（orderQty 一致/不一致）

RFID 推送 EPC
  └─ HttpServer::planAllocOf(epc, sku, bClaim)   ← PlcManager 回调
       · bClaim=false：只读预查（判断是否需要缺口搬迁），**不扣额度**
       · bClaim=true ：锁内"判定 + 扣额度 + 登记在途认领"
  └─ PlcManager 选格
       · 候选 = 映射串 ∪ 计划格口（升序）
       · 计划格口不可用（禁用/锁格）→ moveGap 把未完成件转同 SKU 另一计划格口
       · 取首个 remain>0 → 下发；全满 → 改投 66
       · 日志：选格-按计划分配 / 选格-超计划

PLC 落格反馈
  └─ HttpServer::commitLandedAlloc（PLC 接收线程池，唯一跨线程入口）
       · landed+1（同 EPC 去重）、在途转已落、认出剩余额
       · 有计划且已满 → 异常表 错投超计划
       · 无计划 → 不写落格明细（不进 H7）+ 异常表 错投无计划格口
  └─ 每 30s：sweepPlanAllocClaims() 认领超时清扫 + auditPlanAlloc() 不变量巡检

满箱回传 H7
  └─ clampFullboxQtyToPlan()：按 **本格口** 计划件数封顶（不再用 SKU 总数兜底）

波次边界（切出/新波次/完结/恢复）
  └─ reportPlanAlloc(报告) + clearPlanAllocTable(清表)
```

### 线程规则（★违反即数据错乱）

| 操作 | 允许的线程 |
|---|---|
| `claim` / `release` / `moveGap` / `build` / `clear` / `snapshot` / `planAllocOf(bClaim=true)` | **仅 Qt 主线程** |
| `commitOnLanded` | PLC 反馈接收线程池（**唯一**跨线程入口） |
| `sweepPlanAllocClaims` / `auditPlanAlloc` | 主线程（定时器） |

全表由**单一 `m_allocMutex`** 保护；"判定 + 改数"必须在同一把锁内完成
（这正是修复"同时两件在线超计划"的关键）。

> 选择链路（`trySendToPlcForEpc` 的全部调用点、`handleRfidCarNumReport`、波次生命周期回调）
> 均运行在 Qt 主线程；`sendBatchCodesWithEpcCache` 内的选格/认领因此也在主线程。
> `sendCodeInfo` 若走发送线程池，其**失败结果不直接改表**，而是入队
> `m_allocPendingRelease`，由主线程（清扫定时器）统一释放 —— 保证写操作线程单一。

## 四、可追溯设计

| 层 | 承载 | 能回答的问题 |
|---|---|---|
| 决策层（日志 `HTTP_*.log` / `PLC_*.log`） | `[计划分配表] 构建` / `选格-按计划分配` / `选格-超计划` / `计划搬迁` / `[计划分配表] 报告` | 这一件为什么去这个格口？当时各格口的计划/已落/在途/余量是多少？ |
| 账实层（SQLite） | `sorting_records`（EPC/SKU/格口/容器/时间） | 这一件实际落在哪个格口、哪个箱、什么时候 |
| 计划层（SQLite） | `return_wave_item`（**一行 = 一个 (SKU,格口) 对该格口的计划件数 + 该格口类型**） | 这个产品在这个格口计划几件？是正常分拣口还是发货口？ |
| 异常层（SQLite） | `exception_record`（type/order_code/epc/sku/reason/time） | 哪些件需要人工处理？为什么？ |

**计划 vs 实际对账（只读 SQL）**

```sql
-- 每 (SKU,格口)：计划件数 vs 实际落格件数（实际按 EPC 实时 COUNT，不依赖冗余列）
SELECT i.inco, i.grid_num, i.grid_type, i.plan_qty,
       (SELECT COUNT(*) FROM sorting_records s
         WHERE s.order_code = i.order_code AND s.sku = i.inco
           AND CAST(s.grid_num AS INTEGER) = CAST(i.grid_num AS INTEGER)) AS sorted_qty
  FROM return_wave_item i
 WHERE i.order_code = '<波次号>'
 ORDER BY i.inco, i.grid_num;
```

> 该查询正是 `define.h` 的 `SQL_QUERY_SKU_GRID_MAPPING_BY_ORDER`；
> 其中 `sorted_qty` **实时统计** `sorting_records`，因此本模块**不新增任何每件 DB 写**，
> 也不启用 `SortingDatabase::incrementSortedQty`（该函数现网无调用者）。

**异常件"在哪个箱"**：`exception_record` 不含容器列（避免改动 25 处插入点），
容器号在**查询侧**由 `epc` 关联 `sorting_records.boxcode` 得到。

## 五、稳定性设计（现场最关心）

### 5.1 失效隔离与一键回退

| 机制 | 行为 |
|---|---|
| `m_allocValid == false`（未编译 / 编译为空 / 开关关闭） | 所有查表路径**立即退回改造前老逻辑**；**绝不因分配表异常而不发指令或阻塞投线** |
| `allocEnabled=false`（配置） | 全系统行为与改造前逐字一致 → **改 XML 重启即回退**，无需回滚 exe |
| `allocRequirePlanValid=true` | 开工预检发现 `Σ每格口计划 ≠ H4 orderQty` 时**拒绝开工**（默认 false 仅告警） |

### 5.2 脏状态一律"拒绝 + 留痕"，不擦除不静默

| 情形 | 处置 |
|---|---|
| 认领号未知 / 已超时释放 | 落格**照实登记**（账实优先）+ WARN + 异常表 `分配表认领不匹配` |
| 同一 EPC 已有在途认领（重复下发） | 保留原认领、**立即释放本次额度**（防认领泄漏），日志留痕 |
| 格口越界 / 计划件数 ≤ 0 | 该条目不进表（编译期跳过），该 SKU 走老逻辑 |
| 在途认领超上限（`allocMaxInflight`） | ERROR + 强制清扫 + 异常表留痕，防内存/额度泄漏 |

### 5.3 不变量巡检（把"隐性错账"变成"可见告警"）

每 30s（`allocAuditIntervalMs`）巡检一次，**只读、不修改任何状态**；
违规 → ERROR 日志 + 异常表 `type=分配表不变量违反` + UI 汇总条显示违规数。

| # | 不变量 | 含义 |
|---|---|---|
| ① | `landed ≤ planQty` | 箱内实落不得超计划 |
| ② | `landed + reserv ≤ planQty` 且 `remain == planQty−landed−reserv` | 额度自洽（含在途） |
| ③ | 每 SKU `Σ planQty == planTotal` | 计划总数守恒（缺口搬迁只换格口不改总数） |
| ④ | 每 SKU `Σ remain == skuRemain` | 剩余额度自洽 |
| ⑤ | 格口号 ∈ `1..BINDING_SLOT_COUNT` | 编译期已保证（越界不进表） |

### 5.4 生命周期

`clearPlanAllocTable()` 挂在**五处**波次边界（与既有 `clearGridLandedCount()` 完全同一批调用点）：
波次切出 / 新波次落库完成 / H8 完结成功 / 波次取消 / 波次恢复重建前。
清空前若有在途认领残留 → WARN 留痕（提示有件已下发但未收到落格反馈）。

> ★ 注意：新波次落库完成回调是**异步**到达的（在 `waveParsed` 之后），
> 因此该处**只在"表属于别的波次"时才清**，否则会把刚编译好的当前波次计划误清空。

## 六、性能与容量（日万级件 / 单波次 ≤5 万件）

| 项 | 目标 / 实测策略 |
|---|---|
| 单件 RFID→PLC 下发 | 与改造前**持平**，p99 < 1000ms（现场 1s 硬窗口不破）；用现有 `perfSampleRfidToPlc` 观测 |
| 分配表每件主线程开销 | **< 5 µs**；只做哈希查改 + 整数运算，**零** DB / 网络 / 文件 IO |
| 建表 5 万件 | 解析线程内 O(N log N) 编译，**< 2s**，低优先级，不阻塞 PLC/扫描 |
| 落格反馈处理 | DB 往返数**不增加**（本模块不新增每件 DB 写） |
| 分配表常驻内存 | ≈ 3.8 MB / 波次，峰值 < 6 MB |
| 「计划分配表」页刷新 | 空闲（版本未变 / 本页不在前台）≈ **0**；变化时重建 ≤200 行 < 30ms |
| 单波次日志量 | 选格成功日志节流（前 `allocPlanLogTail`=30 条、之后每 `allocPlanLogStep`=500 条）→ 由约 10 万行降到约 1 万行量级；**异常/超计划/搬迁/兜底日志一律逐条保留** |

**实测方法**

1. `python docs\simulate_alloc.py` —— 12 场景离线逻辑验证（不接触现场）。
2. `test\mock_plc.py` + `test\stress_test.ps1` 压 5 万件波次，用日志中的
   `[计划分配表] 构建 … 耗时=…ms` 与 `perfSampleRfidToPlc` 指标核对。
3. UI 页开销：切到该页停留观察（空闲时不应有可感知卡顿）；
   版本未变时 `refreshPlanAllocPage` 直接 return。

## 七、配置项（`config/http_server.xml`，修改后需重启服务）

| 配置 | 默认 | 说明 |
|---|---|---|
| `allocEnabled` | `true` | **总开关**。`false` = 逐字回退改造前"恒取首个格口"行为（应急回退用） |
| `allocRequirePlanValid` | `false` | `true` = 开工预检发现 `Σ每格口计划 ≠ orderQty` 即拒绝开工 |
| `allocGapMoveOnDisabled` | `true` | 计划格口满箱未重绑(禁用)时，未完成件转同 SKU 另一可用计划格口 |
| `allocGapMoveOnLocked` | `true` | 计划格口物理锁格时同样转移 |
| `allocMaxInflight` | `2000` | 在途认领上限（超出 → 强制清扫 + 异常留痕） |
| `allocAuditIntervalMs` | `30000` | 不变量巡检 + 认领清扫周期(ms) |
| `allocClaimTimeoutMs` | `30000` | 认领超时(ms)：下发后迟迟无落格反馈则归还额度 |
| `allocPlanLogTail` | `30` | 选格成功日志前 N 条逐条（0 = 全部逐条） |
| `allocPlanLogStep` | `500` | 之后每 N 条一条（异常类日志不受此限） |

对应宏定义在 `WCS_httpServer/define.h` 的
「★ 2026-09-14 计划分配表（落格结构优化）配置」小节。

## 八、现场排障速查

| 现象 | 先看什么 | 可能原因 / 处置 |
|---|---|---|
| 件全部落在第一个格口 | 有无 `[计划分配表] 构建` 日志 | ① exe 是旧版本；② `allocEnabled=false`；③ H4 该 SKU 未下发 `gridNumber`（计划为 0 则不进表） |
| 日志出现 `分配表未就绪` / 选格走老逻辑 | `m_allocValid` 对应日志 | 分配表编译为空（H4 计划无效）；查 `[计划分配表] 构建` 是否报错 |
| 件被改投 66 但看不出原因 | `选格-超计划` 行的 `分配表=` | 计划格口已满（含在途）；如需更多额度请核对 WMS 计划件数 |
| 计划格口有件但没落满 | `计划搬迁` 日志 + `[计划分配表] 报告` | 计划格口禁用/锁格，未完成件已转同 SKU 其它计划格口；若全部不可用则进 66 |
| 出现 `分配表不变量违反` | 异常表 `type=分配表不变量违反` + `[分配表] 违规:` 明细 | **账实可能已不一致**：按明细人工核对实物与 `sorting_records`，必要时取出多余件 |
| 件数对不上但无预警 | `return_wave_item` + `sorting_records` 对账 SQL（§四） | 核对是否"落错格"被拦（异常表 `错投无计划格口`，该件不上报） |
| 大量 `认领超时释放` | PLC 落格反馈是否正常 | 下发后无反馈 → 检查 PLC 通信/格口物理状态；额度会被归还，件可按原计划重投 |
| 「计划分配表」页空白 | 是否有运行波次 | 无波次时为空属正常；有计划未开工时仍应显示计划与余量 |
| 需要紧急回退 | 配置 `allocEnabled` | 改为 `false` 重启 → 行为与改造前一致（不需要回滚 exe） |

**上线灰度顺序**：离线仿真 → 真实波次干跑对账 → mock 端到端 + 稳定专项 → 现场小波次（≤50 件、含 1 个正常分拣口 + 1 个发货口）用新页与实物箱核对 → 全量。
