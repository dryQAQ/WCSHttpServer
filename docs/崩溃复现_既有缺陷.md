# 崩溃复现与已确认结论（2026-09-14）

> **一句话**：本仓库**当前源码**（不含「计划分配表」改动，即 `HEAD`/`e6dc5b4`）用本机工具链重新编译后，
> 在 mock 全链路回放中**稳定崩溃（C0000005）**；而仓库里**已提交的旧 exe 不崩**。
> 即：**这是一个既有的源码级缺陷，不是「计划分配表」优化引入的**。
>
> ✅ **根因已定位并修复**（见 §六）：`commitNoWait` 的 lambda **按引用捕获栈上局部变量**，
> 而 `ThreadPool::commitNoWait` 实为异步执行 → **use-after-free**。修完实测不再崩溃。

## 六、★ 根因与修复（已确认）

### 6.1 根因

`WCS_httpServer/HttpServer.cpp`（PLC 反馈批处理入口，原第 379 行）：

```cpp
QSet<QString> landedEpcs;
m_pPlcRecvPool->commitNoWait([this, entries, rescanEpcs, &landedEpcs]() {   // ← & 引用捕获
    ...
    landedEpcs.insert(e.code);                       // 任务内写入
    ...
    if (!landedEpcs.isEmpty())
        emit epcsLanded(QStringList(landedEpcs.constBegin(), landedEpcs.constEnd()));
});
```

而 `WCS_httpServer/ThreadPool.h` 第 82-99 行：

```cpp
template<class F, class... Args>
void commitNoWait(F&& f, Args&&... args)
{
    ...
    { std::lock_guard<std::mutex> lock{ _lock }; _tasks.emplace([task] { (*task)(); }); }
    _task_cv.notify_one();
}                       // ← 入队即返回，任务由池内线程【稍后】执行
```

**结论**：`commitNoWait` 只做"入队 + `notify_one`"就返回，**从不等待执行**。
外层函数一返回，栈上 `landedEpcs` 立即析构，工作线程随后 `insert` / 遍历它 →
**use-after-free** → `C0000005`（访问到的地址落在已释放/已复用的堆内存或其内部指针上，
这也解释了为何崩溃点出现在 Qt5Core 内）。

原注释"lambda 无 detach，commitNoWait 保证本帧内执行完"与实现不符，是这次误判的源头。

**为何"每次运行恰好崩 2 次"**：该 lambda 每批落格反馈执行一次；
回放中前两件落格各触发一次 → 2 次 use-after-free。

**为何旧 exe 不崩、新编译才崩**：经典内存错误的表现取决于堆布局与释放时机。
旧二进制与当前源码并非同一版本（`git show HEAD:...` 的 exe 与当前源码编译结果不一致），
新编译的堆布局让这块释放内存立即被复用，于是稳定暴露。

### 6.2 修复

按值捕获**副本**（并把填写动作留在任务内部）：

```cpp
QSet<QString> landedEpcs;
m_pPlcRecvPool->commitNoWait([this, entries, rescanEpcs, landedEpcs]() mutable {
    ... landedEpcs.insert(e.code); ...          // 写的是任务自己那份副本
    if (!landedEpcs.isEmpty())
        emit epcsLanded(QStringList(landedEpcs.constBegin(), landedEpcs.constEnd()));
});
```

- 改动量：**1 处捕获列表 + 1 处 `mutable`**，不改任何业务语义、接口、报文或数据库结构；
- `emit epcsLanded(...)` 是 `Qt::QueuedConnection`，Qt 会再拷一份参数，故按值捕获安全；
- 已全仓扫描同类风险：`commitNoWait` 共 7 处调用，**仅此 1 处**按引用捕获栈变量，其余均按值。

## 七、多波次压测暴露的第二个问题：排队期间件被误投异常口（已修）

### 7.1 现象

多波次压测（连续下发波次，每波次推"计划件数 + 1"件）时：
- 波次 1 正常：`[34, 48, 48, 48, 66]`；
- 波次 2/3 **全部 5 件都被投到 66**，且本波次没有 `[计划分配表] 构建` 日志。

日志显示波次 2/3 被**排队**：
```
新波次排队 orderCode=PPW02377055 qty=4 当前波次=PPW01377034 队列=1
```
（`maybeStartPendingWave` 只在当前波次到达 `FINISHED/CANCELLED` 后才启动待执行队列。）

### 7.2 机理（**注意：其中一部分是测试造数导致，不是缺陷**）

要分清两件事：

| 情形 | 是否缺陷 | 说明 |
|---|---|---|
| **上一波次仍在 SORTING，期间推件** | **不是缺陷** | 件到达时系统无法分辨它属于哪个波次，按"当前波次"处理、计划耗尽即改投 66 —— 语义正确。多波次压测第一版正是这种造数，属于测试不真实。 |
| **上一波次已收尾/未开工，期间推件** | 潜在风险 | 此刻若仍有件上线，会按"上一波次已耗尽的计划"判超计划 → 投 66 + 误写超计划异常账。 |

### 7.3 修复（初版：仅按"当前波次是否执行态"判定）

在 `trySendToPlcForEpc` 增加守卫：**待执行队列非空 且 当前波次不在执行态**
（`IDLE/CREATED/BOUND/ENDING/HELD/CANCEL_PENDING/CANCELLED/FINISHED`）时，
件一律**挂起**（复用既有 `m_pendingRfidPlcEpcs` + `replayPendingRfidPlcEpcs` 链路），
不下发、不投异常口、不写异常账。

> ⚠️ 这一版**不够**：它只覆盖"当前波次非执行态"。若上一波次**仍在 SORTING**，
> 守卫不生效，下一波次的货仍会按上一波次已耗尽的计划被判超计划 → 投 66。
> 客户明确"波次与波次相互隔离、互不影响"后，改为 §7.5 的完整隔离判定（已放在函数最前面）。

### 7.4 修复后实测（`test/e2e_plan_alloc_multi_wave.py`）

| 场景 | 期望 | 实测 |
|---|---|---|
| A 单波次按计划分配（自动开工） | `[34] + [48]×3 + [66]` | **`[34, 48, 48, 48, 66]` 通过** |
| B 上一波次未开工 + 新波次排队 → 推 3 件 | 不得下发、不得误投 66 | **下发 0 条、误投 66 = 0，6 条挂起记录，通过** |

`trySendToPlcForEpc 非执行态不发送 epc=QB001 status=2(已绑定) (已就绪→挂起，恢复分拣后自动补发)`
`RFID推送 已存储未发送(非分拣中) epc=QB002 …`

两场景均：`crash.log` 不增长、进程存活。

### 7.5 ★ 波次隔离（客户确认口径，已实现并验证）

**客户口径**（两条，已确认）：
1. **波次与波次之间相互隔离、互不影响**；现场作业方式：**同一时刻只有一个波次的货上线**。
2. 若**同一 SKU 同时出现在两个波次**，且当前波次已下发到该 SKU
   → **按当前波次处理即可**（不做特殊区分，避免把正常件误挂起）。

因此"下一波次的货"只在**一个明确、无歧义的条件**下才成立：
〔该 SKU **完全不在当前波次的计划里**〕且〔该 SKU 出现在某个排队波次的 SKU 集合里〕
→ 判为下一波次的货 → **挂起**等其所属波次。

反之，**只要当前波次计划里有这个 SKU**（不论还有没有余量），一律按当前波次处理：
- 有余量 → 按计划正常分配；
- 无余量（多投/超计划）→ 维持既有"超计划改投异常口 66"语义。

**实现**（`HttpServer::trySendToPlcForEpc` 函数**最开头**，先于所有其它闸门）：
1. `PendingWave` 增加 `skuSet`：波次入队时从 H4 原始报文轻量提取 `items[].inco`；
2. 到货件解析出 SKU 后按上述唯一条件判定，命中即**挂起**
   （复用 `m_pendingRfidPlcEpcs` + `replayPendingRfidPlcEpcs`），不选格、不下发、不投 66、不写异常账；
3. **为什么必须放在最前面**：既有"非执行态"闸门对 `CREATED/BOUND` 状态会**广播**下发
   （不选格口就发指令），PLC 可能把件导向任意格口；若下一波次的货在此时上线就会被误送。

**验证**（`test/e2e_wave_isolation.py`，三项全部通过）：

| 步骤 | 期望 | 实测 |
|---|---|---|
| A 波次投 2 件 | 按计划 `[34, 48]` | `[34, 48]` ✅ |
| A 自己多投 1 件（无排队波次） | 按老口径进 66 | `[66]` ✅ |
| A 仍在分拣、B 已排队，推 B 的 2 件（不同 SKU） | 挂起、下发 0 条 | **下发 0 条，2 条隔离日志** ✅ |
| A 仍在分拣、C 已排队，推 C 的件（**同 SKU**） | 不被隔离、按当前波次处理（多投进 66） | **新增隔离 0 条，下发 `[66]`** ✅ |

```

epc=B001 sku=… status=3(分拣中) 原因=SKU 不在当前波次计划内且属于排队中的下一波次 待执行队列=1
```

### 7.6 关于"挂起件"（现场理解用）

**挂起件** = 件已被 RFID 读到（EPC→SKU 已查好、存于 `EpcCache`）、
但系统**刻意没有给它下发格口指令**，把它放入 `m_pendingRfidPlcEpcs` 等待之后补发。

**为什么会有**：下发指令必须先"选格口"，而选格口依赖**波次的计划**。件到达时若没有可用的
波次计划，系统只有两个选择：① 硬发一个格口（历史实现对 `CREATED/BOUND` 会**广播**、
不选格口 → PLC 可能把件导向任意格口，件去向不可追溯）；② **挂起等待**。
系统一律选 ②。

因此挂起件**不是异常件、也不写异常账**，它是"件来早了，等一等"。触发情形只有两种：
- 件属当前波次，但当前波次**尚未开工 / 正在收尾**；
- 件属于**排队中的下一波次**（本节的波次隔离场景）。

补发点：`replayPendingRfidPlcEpcs()`（波次进入 `SORTING` 时触发）。

> ⚠️ 边界：`EpcCache` TTL 为 300s；若跨波次等待超过 5 分钟，缓存过期后该件不会被补发
> （补发时 `isReadyForPlc` 不通过即跳过，日志有记录）。需要更长等待时应调大 TTL。

### 7.7 挂起件补发：按**新波次的格口**落格（同一 SKU 换格口场景）

**现场问题**：同一 SKU 在新波次里的格口可能**完全不同**（例如 A 波 `034/048` → B 波 `035/049`）。
被挂起的件在补发时必须按**新波次的计划重新选格**，不能沿用上一波次的格口。

**实现**：
- 补发入口 `replayPendingRfidPlcEpcs()` 改为调用
  `trySendToPlcForEpcInternal(epc, /*bReplayed=*/true)`；
- `bReplayed=true` 时**跳过波次隔离判定**（该判定只用于"新到货件"分流，
  不适用于已判定归属的补发件）——否则会出现"所属波次已开工、但又有别的波次在排队时
  被自己的隔离逻辑二次拦下"的死循环；
- 其余校验与选格完全一致 ⇒ **选格始终读当前波次的分配表**，
  所以同一 SKU 换格口时，补发件落的是**新波次的新格口**；
- 若新波次的计划里**没有**该 SKU，则该件会走到既有"SKU 未在 GridBuffer 中找到"分支
  （写异常表留痕），不会静默丢失。

**验证状态（如实说明）**：

| 项 | 状态 |
|---|---|
| 隔离判定命中 → 件被挂起、不下发、不进 66、不被广播 | ✅ 已实测（§7.5 表） |
| 挂起件**保留**在待补发集合中 | ✅ 已实测（补发入口 `count=%d` 有记录） |
| 补发时**跳过隔离判定**、按当前波次最新计划选格 | ✅ 代码路径已实现并编译通过；**mock 无法端到端驱动** |
| 取消波次时先重置 WaveManager 再清 GridBuffer（避免下一波次落库 `items=0`） | ✅ 已修（见下） |

**为什么 mock 驱动不了"补发"这一步**：触发补发需要波次进入 `SORTING`，
而当前波次从 `SORTING` 出发的合法迁移只有 `FULLBOX_SYNC / ENDING / HELD`
（见 `WaveManager::setState`），**不允许直接取消**；`ENDING→FINISHED` 又要走 H8 回传。
即"结束当前波次"只能靠人工「结束任务」。因此该步需**人工验证**：

1. 下发波次 A（如 `034:1 + 048:1`），点「开始分拣」，投满 A 的件；
2. 下发波次 B（**同 SKU、格口不同**，如 `035:1 + 049:1`）→ 应进「待执行队列」；
3. 投 B 的件 → 应出现
   `波次隔离：本件挂起（… 原因=SKU 不在当前波次计划内且属于排队中的下一波次 …）`，
   且**没有** PLC 下发、**没有**进 66；
4. 点「结束任务」结束 A → B 自动成为当前波次；
5. 点「开始分拣」（或按现场流程开工）→ 应出现
   `RFID挂起EPC补发 恢复分拣 count=N` 与 `RFID挂起补发成功 epc=…（按当前波次最新计划选格）`；
6. **核对补发件落在 B 的格口（035/049）**，而不是 A 的（034/048）。

**测试专用钩子**（生产不得设置；不设置时行为与以往完全一致）：
- `WCS_E2E_AUTOSORT`：波次落库后自动开工（原有钩子）；
- `WCS_E2E_AUTOSORT_ANY`：任意路径（含"接替为当前波次"）均自动开工；
- `WCS_E2E_ALLOW_CANCEL_SORTING`：允许取消分拣中的波次（受状态机限制，
  仅对 `CREATED/BOUND` 有效）。

### 7.8 顺带修复：取消波次导致下一波次落库 `items=0`

**现象**（`test/e2e_pending_replay.py` 实测复现）：
取消当前波次后，被接替的排队波次在 DB 里落成 **0 条明细**
（`[SortingDB] 波次明细写入成功 orderCode=… count=0`）→ 该波次之后"恢复波次"会因
明细为空被拒绝，只能让 WMS 重下发。

**根因**：`handleCancelWave` 里 **GridBuffer 先清空、WaveManager 后重置**。
而 `m_pWaveMgr->clearWave()` 会发出 `waveStatusChanged` → 触发
`maybeStartPendingWave()` 立刻把排队波次交给解析线程；等它解析完去落库时，
读 `m_pBuffer->activeMap()` 已是被清空的缓冲。

**修复**：调换顺序 —— **先重置 WaveManager（释放排队波次去解析），再清 GridBuffer**。
这样本轮清空只作用于"已取消的旧波次"，下一波次的映射在其后写入缓冲，落库读到的是自己。
