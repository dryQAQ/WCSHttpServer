# 「切换波次 / 刷新状态」明显卡顿 —— 排查与修复

> 版本：2026-09-15
> 现象：点击「波次数据记录」→「切换波次」时界面明显卡顿（数秒无响应）
> 结论：**不是当天 RFID/绑定改动引起的**；根因是「波次数据记录」列表刷新时为**每个波次各查 3 次数据库**（N+1），
> 全部同步跑在 UI 线程上。实测 108 个波次 ≈ 320 次往返 ≈ **6 秒以上界面冻结**。
> 修复：改为 3 条 GROUP BY 批量查询 + 关掉每次 DB 往返的 3 行诊断日志（默认关闭，可用环境变量恢复）。

---

## 一、排查过程（用现场日志定量定位）

### 1.1 现场日志证据（2026-09-15 17:19:39 那次切换）

`release_WcsHttpServer/log/HTTP/http.log`：

```
17:19:39.550 [HttpServer::buildPlanAllocTable]   [计划分配表] 构建 order=PP2026MOCK96990 ... 耗时=0ms
17:19:39.556 [HttpServer::resumeUnfinishedWave]  切换波次 order=... 历史绑定记录 0 个（物理当前绑定 0 个保持不变）
17:19:39.563 [HttpServer::resumeUnfinishedWave]  恢复波次成功 order=... target=2(已绑定)
```

→ **服务端"切换波次"本身只用了约 13ms**（39.550 → 39.563），不是切换逻辑慢。

`release_WcsHttpServer/log/DataBase/data.log` 同一时刻（复制快照后统计）：

```
17:19:39 这一秒内 data.log 行数 = 63（= 21 次 DB 往返 × 3 行诊断日志）
17:19:39.563 起持续到 17:19:42.97+，每约 60ms 出现 3 次 runOnDbThread 往返（= 每波次 3 次查询）
```

→ 切换完成后，UI 立刻执行 `onRefreshWaveRecords()`（刷新波次列表），
**每 60ms 才处理完一个波次**；当天 DB 里 `return_wave` 有 **108 个波次** ⇒ 约 **6.5 秒** 的界面冻结。
这就是"点一下切换，界面卡住几秒"的直接原因。

### 1.2 为什么是"每波次 3 次查询"

`MainWindow::onRefreshWaveRecords()` 原实现（每行波次都做）：

| 查询 | 用途 |
| --- | --- |
| `getWaveFullboxOutbox(orderCode)` | H7 满箱状态（成功/待发/失败） |
| `getWaveEndOutbox(orderCode)` | H8 完结状态 |
| `queryExceptions(orderCode, …, limit=1000)` | 「处理/异常口」件数（未闭环 PLC 判定失败去重 EPC） |

3 次 × 108 波次 = **324 次同步 DB 往返**，且每次往返经 `runOnDbThread`（阻塞等待 DB 线程）
并写 3 行诊断日志；现场 `data.log` 已达 36MB，逐行落盘约 6ms ⇒ 单次往返约 20ms。

### 1.3 与"当天改动"的关系（核实结论）

| 检查项 | 结论 |
| --- | --- |
| 当天改动的文件 | `RfidPushClient`（EPC 识别/原始报文）、`SortingDatabase`（rfid_raw）、`HttpServer`（原始报文留痕 + 启动绑定恢复）、`HttpClient`（响应 EPC 归一）、`MainWindow`（原文显示/弹窗页签）等 |
| `onRefreshWaveRecords` / `getWaveFullboxOutbox` / `getWaveEndOutbox` / `getAllWaves` / `queryExceptions` 是否被改过 | **没有**（`git diff -U0` 的改动行段不含该函数区间 3647~3830） |
| 该 N+1 的来源 | 2026-09-08 / 09-13 的既有实现；随着波次累积到 108 条，代价线性放大 → 今天才明显 |
| 当天新增的 RFID 留痕是否会拖慢切换 | 不影响：`rfid_raw` 只在 RFID 推送帧到达时入队（1s 攒批落库），切换路径不涉及；且队列空时定时器只做一次日期比较 |

## 二、修复内容

### 2.1 列表刷新：N+1 → 3 条批量查询

新增 `SortingDatabase` 批量接口（各一次 GROUP BY，覆盖全部波次）：

| 接口 | SQL | 说明 |
| --- | --- | --- |
| `getFullboxStatusCountAll(bool* ok)` | `SELECT order_code, status, COUNT(*) FROM outbox_fullbox GROUP BY order_code, status` | H7 状态计数（成功/待发/失败） |
| `getEndStatusCountAll(bool* ok)` | 同上（outbox_end） | H8 状态计数 |
| `getPendingExceptionCountAll(bool* ok)` | `SELECT order_code, COUNT(DISTINCT epc) FROM exception_record WHERE epc<>'' AND handled=0 AND type IN ('plc_no_grid','plc_info_incomplete') GROUP BY order_code` | 各波次"仍在异常口"件数 |

要点：

- 走**线程局部只读连接**（`queryDb()`，WAL 并行读）：不占用 DB 写线程、不产生 `runOnDbThread` 往返与诊断日志。
- 统计口径与逐波次版本**逐条对齐**：`success`→成功、`failed`→失败、其余（pending/cancelled…）→待发；
  异常只计 PLC 判定失败两类且 `handled=0`，按 EPC 去重。
- 批量查询不可用时（极端情况）**自动退回原逐波次查询**，行为与改造前完全一致（不会显示错数）。
- 附带修正：原逐波次异常统计受 `LIMIT 1000` 限制（异常多的波次会少算），批量版为精确去重计数。

### 2.2 关掉"每次 DB 往返 3 行诊断日志"（默认关闭）

`SortingDatabase.h::runOnDbThread()` 每次调用会写 3 行诊断
（`提交操作` / `开始执行` / `执行完成`）。现场实测这 3 行约占每次往返 20ms 中的绝大部分。

- 现默认**不再输出**（错误/告警日志不受影响）；
- 现场需要排查 DB 线程问题时：设环境变量 **`WCS_DB_TRACE=1`** 后重启程序即恢复全部诊断行；
- 附带收益：`data.log` 不再被诊断噪声撑大（原已 36MB）。

## 三、效果

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 「波次数据记录」刷新（108 波次） | 324 次同步往返，约 6 秒界面冻结 | **3 次只读查询**，毫秒级 |
| 单次 DB 往返（其他 UI 查询，如波次摘要 5 次查询） | 约 20ms（含 3 行日志落盘） | 约 1ms |
| 日志量 | 每次往返 3 行（36MB/天级） | 常态不再增长（错误/告警仍照常） |

自测实测（`tests/test_wave_records_batch.cpp`，60 个波次）：
**批量 3 次查询 ≈ 0.0ms ／ 逐波次 180 次查询 ≈ 45–74ms**（测试进程内无日志落盘，故现场收益更大）。

## 四、验证方式（可重复执行）

```
tests\run_tests.bat
```

新增 `tests/test_wave_records_batch.cpp`（18 项断言）：

1. 造 4 个波次（分拣中/已完结/已取消/无报文）× 多状态出站报文 + 异常（含重复 EPC、已闭环、类型不符）；
2. 断言批量结果的每项计数（含 `cancelled` 归"待发"、已闭环不计入、同 EPC 去重、无记录波次无键）；
3. **与逐波次"金标准"逻辑逐波次比对**（H7/H8/处理件数三项全部一致）——保证口径零回归；
4. 造 60 个波次对比耗时，断言"批量 < 逐波次"且统计仍正确。

自测同时发现并修复了一个既有隐患：`insertOutboxFullbox` / `insertOutboxEnd` 绑定 null `QString`
会被 `NOT NULL` 拒绝而**静默丢报文**（现已统一做空串归一 + 失败落 Data_ERROR 日志）。

## 五、现场确认步骤

1. 更新程序后，进入「波次数据记录」页；
2. 点击「刷新状态」或选中一条波次点「切换」——列表应在**无感知的时间内**刷新完（不再数秒卡住）；
3. 若仍需观察 DB 线程往返（排查用）：设置环境变量 `WCS_DB_TRACE=1` 重启，`log/DataBase/data.log`
   会恢复输出 `runOnDbThread 提交操作/开始执行/执行完成`；
4. 若仍感觉卡顿，请记录：操作时刻 + `log/HTTP/http.log` 中该时刻前后的 `耗时=` 行 + 波次条数，
   按本文方法（统计 `data.log` 每秒往返次数）即可继续定位。
