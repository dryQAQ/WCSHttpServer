# 格口绑定「波次归属」丢失 → 切回不回溯：根因取证与修复（2026-09-17）

> 现场问题原文：**"历史波次任务和该波次下的格口绑定状态以及显示并不会随切回而回溯过来，有时还会清空"**；
> 客户追问两点：**"格口绑定是否带上波次号保存？"**、**"是不是数据库设计问题？"**
> 相关文件：`WCS_httpServer/HttpServer.cpp`、`SortingDatabase.cpp/.h`、`define.h`、`MainWindow.cpp/.h`、
> `tests/BindingPanelPolicy.h`、`tests/test_restart_resume_db.cpp`、`docs/wave_bind_audit.py`
>
> 本文所有结论均来自**现场运行数据**取证（`release_WcsHttpServer/data/sorting_records.db` +
> `log/HTTP/http.log` + `log/DataBase/data.log`），不是设计推演。
> ★ 本文更正了 `docs/意外关闭重启_继续上次任务.md` §3.3/§3.4 与
> `docs/波次归属与切回回溯_评估结论.md` §2 中"切回必然恢复绑定"的结论。

---

## 一、结论（先看这 5 句）

1. **不是表结构问题**：`grid_box_bind` 本来就带 `order_code`（波次号）+ `active` + 绑定/解绑时间，
   1718 行 / 66 格口的规模也不需要改表。**问题全在写入路径与取数口径**。
2. **绑定写入曾经"整行丢失"**：`order_code` 是 `NOT NULL`，H6 到达时若内存无波次就绑 NULL
   → `NOT NULL constraint failed` → **整行没进库**（09-17 04:28 有 93 条这种失败）。
3. **归属值当时是"猜"的**：H6 报文 `BindingLatticePort?latticehole=…&boxcode=…` **不含波次号**，
   WCS 只能取"内存当前波次"；取不到就走"120s 切出窗口"记到刚切出的波次
   → **把下一个波次的绑定记到了上一个波次**（09-15 23:53 的 66 行 H6 实为 `456456` 的绑定，
   却挂在 `6565656` 名下）。
4. **切回取数是"全有或全无"**：旧主口径要求"该格全表最后一条绑定属本波次"，
   实测 14 个历史波次里 13 个返回 0 行；一旦"部分命中"，旧实现整体替换内存绑定
   → 其余格口全变"未绑定"（**这就是"有时还会清空"**）。
5. **修复后**：H6 只负责"物理绑定落库"（归属取不到就空串保留、不丢行）；
   **H4 到达时**把"本会话内、当前生效、尚未归属"的绑定**补记/纠偏**给该波次；
   切回按"每格取本波次内最后一条"恢复；列表新增「格口绑定」列 + 「查看绑定」只读弹窗。
   全程**不新增表、不加冗余波次列、不自动改历史数据**。

## 二、证据链（可逐条复核）

### 2.1 绑定行整行丢失（NULL → NOT NULL 约束）

```
log/DataBase/data.log
2026-09-17 04:28:13.803 [ERROR] [SortingDB] bindGridBox 插入失败 grid=047 box=H-01-2047
    err=NOT NULL constraint failed: grid_box_bind.order_code Unable to fetch row
...（同一批 93 条，04:28:13 ~ 04:28:16；随后 04:28:17 才收到该波次的 H4）
```
→ `grid_box_bind` 里**一行都没有**，切回自然恢复不出绑定（现场波次 `789`，已落格 168 件）。

### 2.2 120s「切出窗口归属」把新波次的绑定记给了旧波次（致命）

```
log/HTTP/http.log
23:52:22.057  H6 grid=001 order=（空）
23:52:22.668  H4  orderCode=6565656            ← 6565656 成为当前波次
23:53:30.523  新任务：切出 6565656 status=8    ← 切出窗口 armed（m_switchingOutOrderCode=6565656）
23:53:48.304 ~ 23:54:02.050   H6 × 66（grids=001~066, box=H-01-2001~2066）
     "内存波次已切出，H6 绑定归入刚切出的波次 order=6565656"（66 条 WARN）
23:54:02.276  H4  orderCode=456456  orderQty=1320   ← 456456 成为当前波次，但它 0 行绑定
2026-09-16 21:24:18  切回 456456：
     "切回波次无任何绑定可恢复 order=456456（DB 无绑定记录/无活跃绑定）——保持未绑定，等 WMS 下发 H6"
```
数据库现状完全吻合（`SELECT order_code, COUNT(*) FROM grid_box_bind GROUP BY order_code`）：

| 波次 | 状态 | 绑定行 | 已落格 | 结论 |
| --- | --- | --- | --- | --- |
| `456456` | 分拣中(3) | **0** | 1288 | 那 66 行被记到了 `6565656` 名下 |
| `789` | 分拣中(3) | **0** | 168 | 整行丢失（§2.1） |
| `PP2026MOCK823` | 分拣中(3) | 0 | 0 | 同类 |
| `6565656` | 已完成(8) | 66 | 12 | **含误归属行**（时间 23:53:48~23:54:02） |
| `PP202688940581` | 分拣中(3) | 65 | 26000 | 同类误归属（09-09 16:03:44~57 的 65 行，紧随其后 16:03:58 下发了 `PP2026MOCK589`） |

> 用 `python docs/wave_bind_audit.py` 可一键复核上述两类嫌疑（**只读**，不修改数据）。

### 2.3 取数口径"全有或全无"（"有时还会清空"的直接原因）

对真实库执行旧主口径 SQL（`SQL_SELECT_BINDS_BY_ORDER_ACTIVE`）：

| 波次 | 绑定行 | 旧主口径返回 | 本波次口径返回 |
| --- | --- | --- | --- |
| `PP202600000593` | 334 | **0** | 66 |
| `PP202600000588` | 66 | **0** | 66 |
| `PP202600000587` | 75 | **0** | 66 |
| `PP202600000580` | 113 | **0** | 65 |
| `PP202600000574` | 173 | **0** | 66 |
| `PP202688487344` 等 | 3 | **0** | 3 |

原因：只要该格口被**任何一个更晚的波次**绑过，旧口径就不再命中。
而它一旦"部分命中"（一部分格口命中、一部分被更晚波次覆盖），
`resumeUnfinishedWave` 会走该分支并 `loadContainerBindings(部分集合)`（**赋值不是合并**）
→ 其余格口全部变"未绑定"。

### 2.4 数学关系（修复口径为何安全）

"每格全表最后一条属本波次" ⇒ 该行必然也是"本波次内最后一条"
⇒ `getBindsByOrderActive() ⊂ getBindsByOrder()`
⇒ **先取后者绝不会漏格口**（前者降级为"确认口径"，只用于日志标签与命中数统计）。

## 三、修复方案（已实施）

### 3.1 归属写入规则（新口径，单一可测）

| 时刻 | 规则 |
| --- | --- |
| H6 到达，内存**有**当前波次 W | 归属 = W（原行为不变） |
| H6 到达，内存无波次、在 **120s 切出窗口**内 | 归属 = 刚切出波次 A（**保留**：09-15 23:53 确实有 66 条 H6 靠它才落库），但**标记为可纠偏**（同时记录 `m_switchOutTime`） |
| H6 到达，内存无波次、不在窗口内 | 归属 = `''`（**行保留**，不猜；H4 到达时补齐） |
| H6 **报文自带波次号**（新增可选参数） | 归属 = 报文值（优先级最高；WMS 不改也能跑） |
| **H4 到达（波次落库完成）** | **归属补齐/纠偏**，见 §3.2 |

H6 可选带波次号：`orderCode` / `order_code` / `waveCode`（query 参数或 JSON body 均可）。
现场 WMS 若能在 H6 上带上该字段，归属将**不再依赖任何推断**（这是客户"绑定带上波次号保存"诉求的协议侧答案；
WCS 侧已实现并兼容）。

### 3.2 归属补齐/纠偏（唯一新增的写入路径）

时机：`HttpServer::onWavePersistenceFinished()`（H4 到达、波次落库完成）→
`attributePendingBindsToWave(orderCode)` → `SortingDatabase::attributeBindsToWave(...)`，
**在 `restoreBindsIfEmpty()` 之前**执行。

```sql
UPDATE grid_box_bind SET order_code = ?          -- 1: 本波次 W
 WHERE active = 1
   AND bind_time >= ?                            -- 2: 本次会话启动时刻（历史行永不改判）
   AND (order_code = ''                          --    a) H6 早于 H4 → 空归属（789 型）
        OR (order_code = ? AND order_code <> ''  --    b) 切出窗口内的误归属（456456 型）
            AND bind_time >= ?))                 -- 4: 切出时刻
   AND grid_num NOT IN (SELECT grid_num FROM grid_box_bind WHERE order_code = ?)  -- 5: W
```

与"**历史数据不得被粘贴进其它波次**"铁律共存的四条约束：
1. 只处理 `active=1`（此刻物理生效）**且 `bind_time >= 本次会话启动时刻`** 的行；
2. 只处理"空归属"或"切出窗口内产生、属于本次投递的误归属"两类；已归属且不在窗口内的行**永不改判**；
3. 只改 `order_code`，**不新增/不删除行**（行数只可能不变）；
4. 该格口若已存在本波次自己的记录 → **跳过**（不把已在用的记录改错）。

审计留痕：`data.log` 打候选明细、`http.log` + UI 日志打
`[绑定归属] 波次 W：已把 N 个格口的绑定补记到本波次（…）——仅补归属，未新增或删除任何绑定行`。

**有意取舍（必须写清）**：切出窗口内的行无法从时间上区分"是 A 的重发"还是"即将下发的 B 的投递"；
现场实测后者占绝对多数，因此统一改判给紧随其后的 H4 波次
（`tests/test_restart_resume_db.cpp` 用例⑯ 已把这条取舍写成断言，避免后人误改）。

### 3.3 切回取数（主口径修正）

| 级别 | 来源 | 是否写库 | 命中场景 |
| --- | --- | --- | --- |
| 主口径 | `getBindsByOrder()`：每格取**本波次内**最后一条（箱号非空） | 否 | 正常路径；含"已被更晚波次重新绑定"的格口 |
| 兜底 | `getAllActiveBinds()`：DB 当前 `active=1` 的绑定 | 否 | 该波次确实没有任何绑定记录（H6 归属从未落库） |
| 全空 | 保持未绑定 + **明确告警**（不再静默） | 否 | 库中亦无活跃绑定 → 等 WMS 下发 H6 |

日志/弹窗显式标注来源与数量：
```
切回波次恢复容器绑定 order=X count=66（来源=本波次的绑定记录；其中被更晚波次覆盖=0 个；恢复前物理绑定=0 个）
[切换] 波次 X **没有任何绑定记录**（H6 归属落空/当时未绑定）——已按现场当前物理绑定显示 32 个（**不是本波次的记录**…）
```

### 3.4 UI：让"该波次的绑定状态"可见、可回溯

> ★ 2026-09-17 现场口径变更：**「格口绑定」列与「查看绑定」按钮默认隐藏**（现场要求列表更简洁）。

> 隐藏只影响界面入口，**不影响本次的缺陷修复**（归属补齐/纠偏、切回主口径、落库失败告警照常生效）。
> 现场若要核对某波次绑了哪些容器，用只读脚本 `docs/wave_bind_audit.py`（不改数据）。

| 位置 | 内容 |

### 3.5 数据留存与历史核查

* 新增 **只读**脚本 `docs/wave_bind_audit.py`：
  * `A 类`：非终态 + 绑定行=0 → **切回将无法恢复绑定**（本库命中 `456456`/`789`/`PP2026MOCK823`/`PP2026MOCK589`/`PP2026E2E001`/`WAVE20260819163103`）；
  * `B 类`：某波次有一段批量绑定（默认 ≥20 行、跨度 ≤180s），紧随其后（≤300s）下发的另一波次绑定行=0
    → **疑似误归属**（本库命中 `6565656→456456`、`PP202688940581→PP2026MOCK589`）；
  * 输出**建议的人工修复 SQL（只打印、不执行）**与只读复核 SQL；退出码 0/2。
* **默认不改历史数据**：是否清洗由客户确认后手工执行（先备份 DB、逐条核对箱号清单）。
  A 类历史波次无法事后还原（当时就没落库），处置 = 让 WMS 重发 H6。

## 五、已知边界（不在本次改动）

1. **H6 不含波次号时，归属仍依赖运行时判定**：极端情形（"上一个波次的重发 H6"与"下一个波次的投递 H6"
   在 120s 窗口内混在一起）无法从数据上区分，统一按"属于即将下发的波次"处理（§3.2 取舍）。
   彻底解法 = WMS 在 H6 带上波次号（WCS 已支持）。
2. 若该格口在本波次**已有记录**，纠偏会跳过该格 → 该格保留本波次更早的那口箱（与内存当前箱可能不同）；
   日志会标出跳过行，可用「查看绑定」核对。
3. 异步落库窗口内断电 → 该次 H6 仍可能没落库（与既有边界一致，不做同步化改造）。
4. 历史已误归属的行**不自动改**；只读脚本会报出并给出 SQL。
5. 切回"借用物理当前绑定显示"仍是显示态（不写库），UI 已明确标注"不是本波次的记录"。
6. `getBindsByOrderActive()` 仍保留（作确认口径/单测），但**不再作为切回主口径**；
   `SQL_SELECT_BINDS_BY_ORDER` 补了 `boxcode <> ''`（防御，当前无空箱号墓碑行）。
