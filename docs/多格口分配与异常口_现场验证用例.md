# 同品多格口按计划分配 + 66 号异常口 —— 现场验证用例

- 版本基线：提交 `a3d13af`（`[bug] 同品多格口按「各格口计划件数」分配落格…`）
- 适用前提：`config/http_server.xml` 中
  - `<sortingOverplanPolicy>exception</sortingOverplanPolicy>`
  - `<exceptionGrid>66</exceptionGrid>`
  - 修改后**需重启服务**生效
- 编译要求：必须用本提交的源码重新编译 `WCS_httpServer.exe`（线上 09-14 07:50 的 exe 不含本逻辑）
- 日志位置：`release_WcsHttpServer/log/`（`HTTP_*.log` / `PLC_*.log` / `WAVE_ITEM/`）

> 术语：**内部格口 key** = 3 位补零（`034`、`066`）；**WMS 格口编码** = 前缀+3 位（`22034`、`22066`）。
> 日志里两者都会出现，`22034` 与 `034` 是同一个格口。

## 用例 1：同品多格口按计划件数分配（核心）

### 造数要求
H4（`InsertWaveInfo`）下发的 items 中，至少构造一个 SKU **按多个格口分别计划**，例如：

```json
{ "inco": "106101134113101", "gridNum": "22034", "gridNumber": 1, "sobi": "H-01-AB" },
{ "inco": "106101134113101", "gridNum": "22048", "gridNumber": 3, "sobi": "H-01-AB" }
```

即：**SKU `106101134113101` → 034 计划 1 件 + 048 计划 3 件（共 4 件）**。
（这是 09-14 现场真实案例，可直接复现老问题：旧版本 4 件全落 034。）

### 操作
1. H4 下发该波次 → 开始分拣；
2. 把该 SKU 的 4 个不同 EPC 依次投上线（每个 EPC 只投一次）。

### 期望日志

**① 解析期**（`WAVE_ITEM` / `HTTP_*.log`）——证明分格口计划被保留：
```
[SKU映射] 同品多格口分配 orderCode=PPxxxxxxxxxx 涉及SKU=N 明细: 106101134113101→[034:1件+048:3件]; …
```

**② 下发期**（`PLC_*.log`）——按计划分配，注意「选中格」与「已落」变化：
```
选格-按计划分配 code=<EPC1> 映射=[22034,22048] 选中格=34 计划=1件 已落=0件 分配表=034:1件/已落0件 048:3件/已落0件
选格-按计划分配 code=<EPC2> 映射=[22034,22048] 选中格=48 计划=3件 已落=0件 分配表=034:1件/已落1件 048:3件/已落0件
选格-按计划分配 code=<EPC3> 映射=[22034,22048] 选中格=48 计划=3件 已落=1件 分配表=034:1件/已落1件 048:3件/已落1件
选格-按计划分配 code=<EPC4> 映射=[22034,22048] 选中格=48 计划=3件 已落=2件 分配表=034:1件/已落1件 048:3件/已落2件
```

**③ 落格期**：`034` 实收 1 件、`048` 实收 3 件（PLC 反馈 `status=1`），**无** `[超计划-预警]` 日志。

### 判定
- ✅ **通过**：4 件按 `1 件 → 034`、`3 件 → 048` 分流；`分配表` 中 `已落` 计数随每次落格递增。
- ❌ **失败**：4 件全部出现在 `034`（说明未走新分配逻辑 → 检查 H4 是否带 `gridNumber`、exe 是否为新编译）。
- ❌ **失败**：`分配表` 中 `已落` 始终为 0（说明 PLC 落格反馈未登记到计数 → 查 `EpcCache` 是否已拿到该 EPC 的 SKU）。

## 用例 2：超计划多余件改投 66 号异常口

### 操作
沿用用例 1 的 SKU（计划 4 件：034×1 + 048×3），**再多投第 5 个 EPC**（同一 SKU、人为多放一件）。

### 期望日志

**① 下发期**（`PLC_*.log`）：
```
选格-超计划 code=<EPC5> 映射=[22034,22048] 分配表=034:1件/已落1件 048:3件/已落3件 → 发往异常口66（不再占用计划格口）
选格 code=<EPC5> 映射=[22034,22048] 选中格=66 原因=超计划[22034,22048]计划格口已满(034:1件/已落1件 048:3件/已落3件)→发往异常口66
```

**② 落格期**（`HTTP_*.log`）：
```
[异常口] 超计划件已真实落入异常口 epc=<EPC5> sku=106101134113101 grid=066 容器=<该口容器号> status=1 该SKU在本口计划=0件 —— 不计已分拣、不写箱内明细、不进 H7 报文，请人工清出
```

**③ UI/异常表**：界面提示 `[异常口] 超计划件已入异常口：EPC …（SKU …）格口066 容器… —— 请现场清出`；`sort_exception` 表新增一条，`type=超计划入异常口`。

### 判定
- ✅ **通过**：第 5 件下发格口 = `066`；落格反馈被识别为异常口件；**该件不出现在任何 H7 报文里**。
- ❌ **失败**：第 5 件仍在 `034`/`048`（计划格口被超出）→ 查 `m_gridLandedNum` 计数是否递增。
- ❌ **失败**：`066` 落格被计入"已分拣"（波次进度 +1）→ 异常口拦截分支未生效，检查 `exceptionGrid` 配置是否被读到（`66` 与 `066` 均可）。
- ⚠️ **注意**：若日志出现 `选格-超计划 … 未配置异常口，按旧逻辑取首个格口…`，说明 `exceptionGrid` 未生效 → 配置未加载或值写成 `0`/空。

## 用例 2B：单格口 SKU 超计划同样改投异常口（常见场景）

### 造数要求
H4 下发一个**只有一个格口**的 SKU，例如：

```json
{ "inco": "115101001502703", "gridNum": "22034", "gridNumber": 2, "sobi": "H-02-CD" }
```

即：SKU `115101001502703` → `034` 计划 **2 件**。
（这正是 09-13 被 WMS 回 `[2107632]…无法分配` 的现场 SKU：当时计划 2 件、实投 3 件、报文里报了 3 件。）

### 操作
投 **3 个**不同 EPC（多放一件）。

### 期望日志
**① 下发期**（`PLC_*.log`）—— 第 3 件不再发往 034：
```
选格-超计划 code=<EPC3> 映射=[22034] 分配表=034:2件/已落2件 → 发往异常口66（不再占用计划格口）
选格 code=<EPC3> 映射=[22034] 选中格=66 原因=超计划[22034]计划格口已满(034:2件/已落2件)→发往异常口66
```
**② 落格期**：前 2 件正常落在 `034`（计入已分拣）；第 3 件落 `066`，走用例 2 的异常口日志。

### 判定
- ✅ **通过**：`034` 只收 2 件；第 3 件下发格口 = `066`；H7 报文里 `034` 该 SKU `qty=2`（等于计划，WMS 不会驳回）。
- ❌ **失败**：第 3 件仍发往 `034`（旧行为）→ 会出现 `[H7裁剪]` 日志（报文只报 2 件），件虽在箱内却**少账**，需人工取出。
- ⚠️ **对照**：若日志出现 `选格-超计划 … 未配置异常口，按旧逻辑取首个格口34（请人工确认多余件）`，
  说明 `exceptionGrid` 未生效 → 见用例 2 的排查项。

## 用例 3：66 号异常口绑定容器（原实现会拒绝，必须通过）

### 操作
WMS 下发 H6（`BindingLatticePort`）：`latticehole=22066&boxcode=<H-xxxx>`

### 期望结果
- HTTP 返回 **200 + 成功 JSON**（**不是** `code=500`）；
- 日志：
```
BindingLatticePort 异常口绑定 latticehole=22066 box=<H-xxxx>（exceptionGrid=66）—— 允许绑定用于收集超计划件；该口落格件不入 H7 报文、需人工清出
```
- UI 提示：`[容器绑定] 格口066 是异常口/强排口，已绑定容器<H-xxxx>（该口只收超计划件，需人工清出、不上传WMS）`

### 判定
- ✅ **通过**：绑定成功、异常口有容器号 → 用例 2 的日志里"容器="能显示出真实箱号，人工可按箱清出。
- ❌ **失败**：仍返回 `500 格口66为异常口/强排口，不支持容器绑定` → 部署的仍是旧 exe。

## 用例 4：异常口不参与 H7 上传（防止 WMS 整条驳回）

### 操作
1. 让用例 2 的异常件落入 `066` 后，对 `066` 触发满箱（PLC 锁格 / UI「重传满箱切换」输入 `66` / 「一键满箱回传」含 066）。

### 期望结果
- 日志（三者之一，取决于触发入口）：
```
满箱回传（H7）跳过 格口066 为异常口(exceptionGrid=66)：异常口件不入上传报文，请人工清出
满箱补发 跳过格口066（异常口，件不上传WMS，请人工清出）
手动满箱 跳过格口066（异常口/强排口，件不上传WMS）
```
- UI 提示同义；**不产生** 任何 `num=22066` 的 H7 报文。

### 判定
- ✅ **通过**：`066` 无 H7 报文；WMS 侧该波次实报数量 ≤ 计划总量。
- ❌ **失败**：出现 `num=22066` 的 H7 → 异常口件已被上传，会造成 WMS 实报超计划 → 立即人工核对并取出。

## 用例 5：一键满箱回传不受影响

### 操作
点击「一键满箱回传」。

### 期望结果
- 正常格口（如 `034`、`048`）各自生成 H7 报文并发送成功；
- `066` 被跳过（用例 4 的日志）；
- 汇总日志形如 `[一键满箱] 执行完成：已发送 X 个格口…跳过无记录 Y 个…`，其中 Y 包含 066。

### 判定
- ✅ **通过**：其它格口功能完全不受 066 影响；没有因为 066 导致整批回传中止。

## 用例 6：波次面板「预警」口径

### 操作
制造一次**真正的**误落：让某个 SKU 的件落到**非计划格口**（例如把已判去 066 的件人工硬塞进 034），使 `034` 该 SKU 实落 > 本格口计划。

### 期望结果
- 波次面板 `预警:` 数字 > 0，`查看` 按钮可点；
- 明细表列：`格口号 / 容器号 / SKU编码 / 本格口计划 / SKU总计划 / 实际落格件数 / 多余件数`；
- 日志：
```
[超计划-预警] 格口034 容器<H-xxxx> SKU=… EPC=… 本格口计划1件(SKU总计划4件) 实际落格2件 多余1件 → 已登记预警；该多余件不进入上传报文，请现场取出
```

### 判定
- ✅ **通过**：「本格口计划」= 1（而不是 SKU 总数 4）；异常口 `066` 的件**不**计入预警条目。
- ❌ **失败**：「本格口计划」显示为 4（多格口场景失真）→ planQtyPerGrid 未生效。

## 用例 7：波次恢复（切换波次/重启后继续）

### 操作
分拣中途「切换波次」，再切回该波次（走 `resumeUnfinishedWave`）。

### 期望日志
```
恢复波次 同品多格口分配 order=PPxxxxxxxxxx 涉及SKU=N 明细: 106101134113101→[034:1件+048:3件]
```

### 判定
- ✅ **通过**：恢复后剩余件的 `选格-按计划分配` 仍在计划格口内。
- ⚠️ **已知限制**：恢复时"已落格计数"从 0 重新开始（PLC 反馈历史不会重放），
  因此恢复后剩余件会**优先补向计划里的靠前格口**。若该 SKU 已全部落完、没有剩余件，则无影响。

## 附：日志一键核对脚本

仓库内 `docs/verify_multi_grid.ps1` 可对一份运行日志做静态核对（只读，不改任何文件）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File docs\verify_multi_grid.ps1 -LogDir release_WcsHttpServer\log
```

输出五段：
1. **H4 同品多格口清单** —— 哪些 SKU 拆了多格口、每个格口各计划几件（验证解析期分配表被正确保留）；
2. **按计划分配统计** —— 下发次数与选中格口分布（若多格口 SKU 存在却 0 次，说明 exe 仍是旧版）；
3. **超计划改投 + 异常口落格件** —— 含按容器分组的清出清单；
4. **红线检查** —— H7 报文里是否出现异常口编码（出现即不合格，需人工核对）；
5. **误落预警** —— 计划格口内实落超计划的条目与多余件数。

> 该脚本已用「合成日志」验证过五段解析全部命中（含红线命中场景），可直接投入使用。
> 提示：脚本按行匹配，日志轮转后请对**包含该波次的日志目录**运行。
