# 同品多格口按计划分配 + 66 号异常口 —— 现场验证用例

- 版本基线：提交 `a3d13af`（多格口按格口计划件数分配）+ `38aac6d`（单格口超计划改投异常口 / 恢复保留分格口计划）+ 本轮「每格口类型随计划保存 + 开工预检」（见 `git log`）
- 适用前提：`config/http_server.xml` 中
  - `<sortingOverplanPolicy>exception</sortingOverplanPolicy>`
  - `<exceptionGrid>66</exceptionGrid>`
  - 修改后**需重启服务**生效
- 编译要求：必须用本提交的源码重新编译 `WCS_httpServer.exe`（线上 09-14 07:50 的 exe 不含本逻辑）
- 日志位置：`release_WcsHttpServer/log/`（`HTTP_*.log` / `PLC_*.log` / `WAVE_ITEM/`）

> 术语：**内部格口 key** = 3 位补零（`034`、`066`）；**WMS 格口编码** = 前缀+3 位（`22034`、`22066`）。
> 日志里两者都会出现，`22034` 与 `034` 是同一个格口。
>
> 口径（客户确认，2026-09-14）：
> 1. **每个格口都有对应这个产品的数量**；多格口即「**正常分拣（分类）格口 + 发货格口**」，
>    两者各自一份计划件数 → 本系统按**每个格口的计划件数**把件分过去（不是只往第一个格口投）。
> 2. **WMS 会下发 `gridType`**：`0`=分类（正常分拣）/ `2`=发货（`1`=异常保留）；日志中显示为 `034(分类)`、`048(发货)`。
> 3. **66 号（异常口）的件不上传 WMS**：只留本地异常账 + UI 预警 + 日志，人工清出。
>    报文侧做了三层防护：落格反馈识别（不进箱内明细）→ 三处入口跳过（满箱/满箱补发/手动满箱）
>    → `buildFullboxPayload` 报文构建层再兜一道（该层被拦截时调用方不发送，只会留日志）。

## 用例 1：同品多格口按计划件数分配（核心）

### 造数要求
H4（`InsertWaveInfo`）下发的 items 中，至少构造一个 SKU **按多个格口分别计划**，且两个格口是**不同类型**
（客户口径：多格口就是「正常分拣（分类）格口 + 发货格口」，**每个格口各有对应这个产品的数量**）：

```json
{ "inco": "106101134113101", "gridNum": "22034", "gridNumber": 1, "gridType": "0", "sobi": "H-01-AB" },
{ "inco": "106101134113101", "gridNum": "22048", "gridNumber": 3, "gridType": "2", "sobi": "H-01-AB" }
```

即：**SKU `106101134113101` → 034(分类) 计划 1 件 + 048(发货) 计划 3 件（共 4 件）**。
（这是 09-14 现场真实案例，可直接复现老问题：旧版本 4 件全落 034，且发货格口 048 一件未落。）

### 操作
1. H4 下发该波次 → 先确认两个格口都已绑定容器 → 点「开始分拣」；
2. 把该 SKU 的 4 个不同 EPC 依次投上线（每个 EPC 只投一次）。

### 期望日志

**⓪ 开工预检**（点「开始分拣」后立即输出）——证明计划格口都有容器可落：
```
计划格口预检 order=PPxxxxxxxxxx 计划格口=N（分类格口a个+发货格口b个）已绑定=N 未绑定=0 已禁用=0 异常口跳过=0
```
若「未绑定」> 0，会同时弹出/输出告警：`[计划预检] 有 N 个计划格口尚未绑定容器：… —— 请先让 WMS 下发容器绑定`。

**① 解析期**（`WAVE_ITEM` / `HTTP_*.log`）——证明分格口计划**与格口类型**都被保留：
```
[SKU映射] 同品多格口分配 orderCode=PPxxxxxxxxxx 涉及SKU=N 明细(格口(类型):件数): 106101134113101→[034(分类):1件+048(发货):3件]; …
```

**② 下发期**（`PLC_*.log`）——按各格口数量分配，注意「选中格(类型)」与「已落」变化：
```
选格-按计划分配 code=<EPC1> 映射=[22034,22048] 选中格=34(分类) 计划=1件 已落=0件 分配表=034(分类):1件/已落0件 048(发货):3件/已落0件
选格-按计划分配 code=<EPC2> 映射=[22034,22048] 选中格=48(发货) 计划=3件 已落=0件 分配表=034(分类):1件/已落1件 048(发货):3件/已落0件
选格-按计划分配 code=<EPC3> 映射=[22034,22048] 选中格=48(发货) 计划=3件 已落=1件 分配表=034(分类):1件/已落1件 048(发货):3件/已落1件
选格-按计划分配 code=<EPC4> 映射=[22034,22048] 选中格=48(发货) 计划=3件 已落=2件 分配表=034(分类):1件/已落1件 048(发货):3件/已落2件
```

**③ 落格期**：`034` 实收 1 件、`048` 实收 3 件（PLC 反馈 `status=1`），**无** `[超计划-预警]` 日志。

### 判定
- ✅ **通过**：4 件按 `1 件 → 034(分类)`、`3 件 → 048(发货)` 分流；`分配表` 中 `已落` 计数随每次落格递增；类型名与 H4 下发的 `gridType` 一致（`0`→分类、`2`→发货）。
- ❌ **失败**：4 件全部出现在 `034`（说明未走新分配逻辑 → 检查 H4 是否带 `gridNumber`、exe 是否为新编译）。
- ❌ **失败**：`分配表` 中 `已落` 始终为 0（说明 PLC 落格反馈未登记到计数 → 查 `EpcCache` 是否已拿到该 EPC 的 SKU）。
- ❌ **失败**：日志显示的类型与 H4 不符（例如发货口显示成"分类"）→ H4 该行 `gridType` 未下发，或该格口在另一行被覆盖。

## 用例 2：超计划多余件改投 66 号异常口

### 操作
沿用用例 1 的 SKU（计划 4 件：034×1 + 048×3），**再多投第 5 个 EPC**（同一 SKU、人为多放一件）。

### 期望日志

**① 下发期**（`PLC_*.log`）：
```
选格-超计划 code=<EPC5> 映射=[22034,22048] 分配表=034:1件/已落1件 048:3件/已落3件 → 发往异常口66（不再占用计划格口）
选格 code=<EPC5> 映射=[22034,22048] 选中格=66 原因=超计划[22034,22048]计划格口已满(034:1件/已落1件 048:3件/已落3件)→发往异常口66
```

**② 落格期**（`HTTP_*.log`）：
```
[异常口] 超计划件已真实落入异常口 epc=<EPC5> sku=106101134113101 grid=066 容器=<该口容器号> status=1 该SKU在本口计划=0件 —— 不计已分拣、不写箱内明细、不进 H7 报文，请人工清出
```

**③ UI/异常表**：界面提示 `[异常口] 超计划件已入异常口：EPC …（SKU …）格口066 容器… —— 请现场清出`；`sort_exception` 表新增一条，`type=超计划入异常口`。

### 判定
- ✅ **通过**：第 5 件下发格口 = `066`；落格反馈被识别为异常口件；**该件不出现在任何 H7 报文里**。
- ❌ **失败**：第 5 件仍在 `034`/`048`（计划格口被超出）→ 查 `m_gridLandedNum` 计数是否递增。
- ❌ **失败**：`066` 落格被计入"已分拣"（波次进度 +1）→ 异常口拦截分支未生效，检查 `exceptionGrid` 配置是否被读到（`66` 与 `066` 均可）。
- ⚠️ **注意**：若日志出现 `选格-超计划 … 未配置异常口，按旧逻辑取首个格口…`，说明 `exceptionGrid` 未生效 → 配置未加载或值写成 `0`/空。

## 用例 2B：单格口 SKU 超计划同样改投异常口（常见场景）

### 造数要求
H4 下发一个**只有一个格口**的 SKU，例如：

```json
{ "inco": "115101001502703", "gridNum": "22034", "gridNumber": 2, "sobi": "H-02-CD" }
```

即：SKU `115101001502703` → `034` 计划 **2 件**。
（这正是 09-13 被 WMS 回 `[2107632]…无法分配` 的现场 SKU：当时计划 2 件、实投 3 件、报文里报了 3 件。）

### 操作
投 **3 个**不同 EPC（多放一件）。

### 期望日志
**① 下发期**（`PLC_*.log`）—— 第 3 件不再发往 034：
```
选格-超计划 code=<EPC3> 映射=[22034] 分配表=034:2件/已落2件 → 发往异常口66（不再占用计划格口）
选格 code=<EPC3> 映射=[22034] 选中格=66 原因=超计划[22034]计划格口已满(034:2件/已落2件)→发往异常口66
```
**② 落格期**：前 2 件正常落在 `034`（计入已分拣）；第 3 件落 `066`，走用例 2 的异常口日志。

### 判定
- ✅ **通过**：`034` 只收 2 件；第 3 件下发格口 = `066`；H7 报文里 `034` 该 SKU `qty=2`（等于计划，WMS 不会驳回）。
- ❌ **失败**：第 3 件仍发往 `034`（旧行为）→ 会出现 `[H7裁剪]` 日志（报文只报 2 件），件虽在箱内却**少账**，需人工取出。
- ⚠️ **对照**：若日志出现 `选格-超计划 … 未配置异常口，按旧逻辑取首个格口34（请人工确认多余件）`，
  说明 `exceptionGrid` 未生效 → 见用例 2 的排查项。

## 用例 6：波次面板「预警」口径

### 操作
制造一次**真正的**误落：让某个 SKU 的件落到**非计划格口**（例如把已判去 066 的件人工硬塞进 034），使 `034` 该 SKU 实落 > 本格口计划。

### 期望结果
- 波次面板 `预警:` 数字 > 0，`查看` 按钮可点；
- 明细表列：`格口号 / 类型 / 容器号 / SKU编码 / 本格口计划 / SKU总计划 / 实际落格件数 / 多余件数`（`类型` 用于区分分类口/发货口/异常口）；

```
[超计划-预警] 格口034(类型0) 容器<H-xxxx> SKU=… EPC=… 本格口计划1件(SKU总计划4件) 实际落格2件 多余1件 → 已登记预警；该多余件不进入上传报文，请现场取出
```

## 用例 8：落格与计划一致性校验（防止"分类口/发货口"被误判为冲突）

### 背景
旧版本有一段"同品分类vs发货冲突检测"：它在同一映射表内比较同一个条目，**恒不成立**（等于没校验）；
而合并后的 `gridType` 只保留最后一行，也无法反映各格口真实类型。
现改为按「每格口类型 + 每格口计划」判定：

| 情形 | 期望日志 | 是否算异常 |
|---|---|---|
| 件落在**本 SKU 计划内**的格口（含分类口/发货口不同类型） | `落格校验 计划内格口 code=… sku=… grid=034(类型0,计划1件) —— 正常，非冲突` | 否 |
| 件落在**不在计划内**的格口 | `落格校验 实际格口不在该SKU计划内 code=… sku=… 实际=048 计划格口=[22034]（PLC报成功，计已分拣）` | 是（异常表留痕，`type=wrong_grid`） |

### 操作
1. 用例 1 的多格口 SKU 正常投递 → 应全部出现「计划内格口…正常，非冲突」，**不应**出现"冲突"字样；
2. 人为把一件投到该 SKU 计划外的格口（如把只计划了 034 的件投到 048）→ 应出现"实际格口不在该SKU计划内"。

### 判定
- ✅ **通过**：分类口与发货口的正常分落**不产生**任何冲突/异常记录。
- ✅ **通过**：真落错格有明确日志与异常表记录，便于人工追溯。
- ❌ **失败**：正常多格口投递出现 `落错格` 记录 → 该格口未进入 `planQtyPerGrid`（查 H4 是否带 `gridNumber`）。
- ❌ **失败**：落错格既无日志也无异常记录 → `sortingConflictPolicy` 不是 `STRICT_EXCEPTION`（宽松模式只打日志）。

## 用例 9：落格即计时归零（保证二次上传/重投能正常重放）

### 背景
`EpcCache` 的「RFID推送→PLC发送」超时窗口（`PLC_SEND_TIMEOUT_MS`=1s）以 `receivedAt` 为起点。
件已真实落格后这一轮计时已无意义；若不清零，该 EPC 之后被重新推送时会沿用旧的 `receivedAt`，
在重投链路里被立刻判"发送超时"→ 本该重新下发的件反而进不了格口。
现在**所有落格分支**（正常落格 / 无匹配留痕 / 无绑定留痕 / 落错格留痕 / 防重分支 / 超计划落异常口）
都会登记该 EPC，批处理结束后回主线程统一归零。

### 操作
1. 正常投一件，确认落格（PLC `status=1`）；
2. 把**同一件**拿起重新上料（RFID 重推同一 EPC）。

### 期望日志
```
[落格归零] epc=<EPC> 已落格 → 超时计时归0、在途/重发计数清零（本次确为在途件）
重扫重投 二次上传计时归零 epc=<EPC>（1s 超时窗口从本次重扫起算）
```
第二次落格**不应**出现 `PLC发送超时 …入异常格口`。

### 判定
- ✅ **通过**：重投时正常下发指令（`选格-按计划分配 …` 或 `选格 … 选中格=…`）并再次落格；无"发送超时"。
- ❌ **失败**：重投立即报 `PLC发送超时`（elapsed 远大于 1000ms）→ 计时未归零，检查 `[落格归零]` 日志是否存在。
- ❌ **失败**：同一件重投后**格口计划计数被多算**（预警里出现多余件）→ 属正常（计数按 PLC 实测计），按用例 6 处理。

### 对下一波次的影响（客户关注点，已核对）
**不影响**，依据：
| 项 | 波次边界行为 |
|---|---|
| 计时归零本身 | 只改**这一个 EPC** 的条目（`receivedAt`/`sentAt`），不动其它 EPC、不动波次状态/绑定/计数 |
| 在途·冷却·重发计数 | `clearAllEpcRuntimeState()` 在**波次切出 / 新波次落库完成 / H8 完结**三处清空 |
| EpcCache 条目 | 自带 TTL 300s，跨波次自然过期；下一波次同 EPC 按新条目重新起算 |
| 格口禁用（满箱未重绑） | 由 H6 重绑或新波次 `enableAllGrids()` 恢复，与计时归零无关 |
