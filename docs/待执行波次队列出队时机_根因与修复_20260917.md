# 待执行波次队列「出队时机」缺陷 → 点「结束任务」后自动接收下一波、跳过一个波次：根因与修复（2026-09-17）

> 现场问题原文：**"当我多次下发不同波次任务时，我点击结束任务后，系统自动接收了下一个任务波次，
> 此时开关是开始接收任务；当我点击开始接收任务时，又一次接收了下一个任务波次，
> 错误的跳过了一个波次任务数据。"**
> 现场要求：**只有在我点击开始接收任务时，才开始接收波次队列里的任务。**
>
> 相关文件：`WCS_httpServer/PendingWaveQueuePolicy.h`（新增）、`HttpServer.cpp/.h`、`MainWindow.cpp`、
> `tests/test_pending_queue_gate.cpp`（新增）、`tests/run_tests.bat`
>
> 本文结论全部来自**现场运行日志**取证
> （`release_WcsHttpServer/log/HTTP/http.log` 2026-09-17 16:47~16:49 实录），不是设计推演。

---

## 一、结论（先看这 5 句）

1. **缺陷真实存在，且 100% 可复现**：只要"当前波次作业中 + WMS 又下发了下一波"，
   点一次「结束任务」就会**自动接收下一波**（界面此刻显示的是「开始接收任务」）。
2. **根因是出队时机**：旧实现把"波次到达终态（已完结/已取消）"当作出队条件
   （`waveStatusChanged` → `maybeStartPendingWave()`）。而点「结束任务」后 H8 一回成功，
   本波次就变**已完结**，可**接收层此时还没收尾**（`stopReceive()` 要等 H8 回调走完才执行，
   `m_receiving` 仍为 true）→ 队列被这一枪"合法"地打出去了。
3. **跳过一波是二次伤害**：被自动接收的那一波已在内存注册；操作员再点「开始接收任务」时，
   `startReceive()` 会先把这一波**切出**（数据留在 DB，但不再执行），再去执行下一个队首
   → **中间那一波从此再也没有被执行 = 现场看到的"跳过"**。
4. **顺带查出并修复两个既有缺陷**：① `maybeStartPendingWave()` 里 `const PendingWave& pw = first()`
   在 `removeFirst()` 之后继续使用 —— **use-after-free**，日志打印的是"队首之后那一波"的波次号
   （现场据此更确信"跳波次"，且属内存安全问题）；② 波次已在队列里但解析结果晚到时，
   旧代码会**直接丢弃**该波次（仅打一条 WARN）—— 同一类"波次数据消失"。
5. **修复后口径（现场要求）**：出队**只允许**发生在"**接收中** 且 **本次会话没点过「结束任务」**"
   之时；点「结束任务」立刻**冻结**队列，点「开始接收任务」才解冻并执行队首。
   **接收中**波次被 WMS 取消（H5）后自动接替下一波的能力**保留**（`test/e2e_pending_replay.py` 依赖）。

## 二、证据链（可逐条复核）

### 2.1 四个波次，三个排队

```
log/HTTP/http.log
16:47:00.343  新波次排队 orderCode=PP202689634819 qty=422 当前波次=test-001 队列=1
16:47:13.410  新波次排队 orderCode=test-002        qty=422 当前波次=test-001 队列=2
16:47:19.410  新波次排队 orderCode=test-003        qty=422 当前波次=test-001 队列=3
```
→ 当前波次 `test-001`（已分拣 60 件）作业中，WMS 连下 3 个波次，全部进入待执行队列（FIFO）。

### 2.2 点「结束任务」→ H8 成功 → **队列被自动打出去**（缺陷本体）

```
16:48:10.898  完结前满箱补发完成 order=test-001 flushed=0            ← 操作员点「结束任务」→ 发 H8
16:48:10.941  完结回传成功（H8） order=test-001 网络往返=42ms          ← test-001 置「已完结(FINISHED)」
16:48:10.984  自动开始待执行波次 orderCode=PP202689634819 队列剩余=2   ← ★缺陷：此刻界面还是「开始接收任务」
16:48:11.016  停止中，跳过波次状态推进 orderCode=PP202689634819 ok=1   ← 接收层此刻才在收尾（m_receiving 仍 true）
```
→ 第 4 行的"自动开始"发生在**停止接收之前**：操作员没有点任何按钮，系统已经接收并注册了下一波
（`PP202689634819`），波次明细也落了库（`items=32`）。这正是现场说的"系统自动接收了下一个任务波次"。

### 2.3 再点「开始接收任务」→ 上一波被切出、直接跳到下一波（现场说的"跳过"）

```
16:48:22.250  HP-Socket配置: ...                                   ← 操作员点「开始接收任务」→ startReceive()
16:48:22.270  开始接收任务：已切出波次 order=PP202689634819 status=1(已下发) -> 空闲   ← ★被自动接收的那一波被切出
16:48:22.308  自动开始待执行波次 orderCode=test-003 队列剩余=1        ← 日志说 test-003（实为悬垂引用打印错号）
16:48:22.336  [计划分配表] 构建 order=test-002                       ← 真正执行的是 test-002
```
→ **`PP202689634819` 被切出后再也没有被执行**（DB 里停在 `已下发`）——这就是"错误的跳过了一个波次任务数据"。

### 2.4 同一模式循环，`test-003` 也被跳过（操作员只能手工重发）

```
16:48:30.979  完结前满箱补发完成 order=test-002 flushed=0          ← 点「结束任务」
16:48:31.015  完结回传成功（H8） order=test-002
16:48:31.052  自动开始待执行波次 orderCode=test-003 队列剩余=0      ← 又被自动接收（界面仍是「开始接收任务」）
16:48:31.068  停止中，跳过波次状态推进 orderCode=test-003 ok=1
16:48:37.801  开始接收任务：已切出波次 order=test-003 status=1(已下发) -> 空闲      ← 再点开始 → 又被切出，队列已空
16:48:51.007  InsertWaveInfo 覆盖旧波次 orderCode=test-003 oldStatus=1            ← 操作员只能手工重发 test-003
16:48:55.505  新波次排队 orderCode=test-004 ... 队列=1
```
→ 三轮"结束任务/开始接收任务"把 `PP202689634819`、`test-003` 两波**跳过**，且每次都表现为
"开关显示开始接收任务，系统却自己接收了下一波"。

### 2.5 顺带发现的既有缺陷：日志打印了**错的波次号**（悬垂引用 / use-after-free）

```
旧代码（HttpServer::maybeStartPendingWave）：
    const PendingWave& pw = m_pendingWaveQueue.first();   // ← 引用（不是拷贝）
    ... task.rawBody = pw.rawBody; ...
    m_pendingWaveQueue.removeFirst();                     // ← 引用指向的元素已被搬移/释放
    HTTP_LOG_INFO("... orderCode=%s ...", pw.orderCode ...);   // ← 读到的是"新的队首"
```
→ 16:48:22.308 实放 `test-002`，日志却打 `test-003`（新队首）。现场核对日志时会认为"跳号"，
且这是**内存安全问题**（UB）。本次已改为"先整体取出（值拷贝）→ push 失败放回队首"。

### 2.6 顺带发现的既有缺陷：解析晚到的波次被**丢弃**

```
旧代码（waveParsed 接收闸门）：
    if (!m_receiving.load() && !m_replayingPending.load()) { WARN(...); return; }   // ← 波次直接消失
```
→ H4 已被 WMS 成功下发（HTTP 已回 `200 successed`），若收尾后才解析完，旧实现**既不注册也不排队**，
只在日志里留一条 WARN。这是另一条"波次数据被跳过"的通道，本次一并消除（改为放回队列）。

## 三、修复内容

### 3.1 新增口径文件：`WCS_httpServer/PendingWaveQueuePolicy.h`

把"能不能出队"写成**一条可测规则**（纯逻辑，无 Qt/GUI 依赖，产品与测试共用同一份实现）：

| 会话状态 | 判定 | 行为 |
| --- | --- | --- |
| 未点「开始接收任务」（未接收/已收尾停止） | `PDQ_NOT_RECEIVING` | **冻结**：不出队，队列原样保留 |
| 已点「结束任务」（H8 回传等待中/会话已要求结束） | `PDQ_END_REQUESTED` | **冻结**：即便本波次此刻变终态也不出队 |
| 接收中 且 本次会话未点过「结束任务」 | `PDQ_ALLOW` | 放行：终态（已完结 / H5 已取消）后接替下一波 |
| 队列为空 | `PDQ_QUEUE_EMPTY` | 无动作 |

### 3.2 `HttpServer` 改动

| 位置 | 改动 |
| --- | --- |
| `sendEnd()`（点「结束任务」） | **入口即置 `m_endRequested=true`** → 冻结待执行队列（附日志：队列 N 个已冻结）。必须在这里置位：接收层还要等 H8 结果才 `stopReceive()`，其间 `m_receiving` 仍为 true |
| `startReceive()`（点「开始接收任务」） | `m_endRequested=false` **解冻** → 末尾 `maybeStartPendingWave()` 成为**唯一出队时机** |
| `maybeStartPendingWave()` | ① 先过 `pendingDequeueDecision` 闸门，冻结时**只记日志、原样保留队列**；② 修复悬垂引用（`takeFirst()` 值拷贝 + push 失败 `prepend` 回滚） |
| `waveParsed` 接收闸门 | 会话已冻结时**不丢弃**：来自队列重放 → 放回**队首**；来自 HTTP 新到达 → 追加**队尾**（`m_pendingReplayInFlight` 计数区分来源，替代原 `m_replayingPending` 布尔） |
| 入队路径 | 新增唯一入口 `enqueuePendingWave()`（去重 + SKU 集合提取 + 落波次头 + UI 刷新 + 留痕），原内联排队代码与回滚路径共用 |
| 排队提示语 | "当前波次 %3 结束后自动开始" → 改为"点「结束任务」后队列保留不自动执行，再点「开始接收任务」时按顺序执行队首" |

### 3.3 UI 改动（`MainWindow::onViewWaveQueue`）

「查看接收波次队列」弹窗：
* 说明文字改为新口径（"只有点「开始接收任务」时才执行队首"）；
* 新增**冻结提示行**：未接收 / 已点「结束任务」→ 橙色 `● 队列已冻结（原因）：这 N 个波次不会被自动执行，
  点「开始接收任务」后才按队首顺序依次执行`；接收中 → 绿色 `● 队列执行中`。
  判据直接取 `HttpServer::isPendingQueueFrozen()`（与出队判据同源，不会漂移）。

### 3.4 测试

```
tests\run_tests.bat  第 8 项：test_pending_queue_gate.cpp（新增）
 ① 未接收 → 冻结（不出队、队列不动、UI 判据为"冻结"）
 ② 已点「结束任务」→ 终态回调**不**执行任何排队波次；队首仍是现场最早那波；停止接收后队列顺序不变
 ③ 接收中且未点结束 → 放行（H5 取消自动接替下一波：既有能力保留）
 ④ 现场时序复现：4 波次依次 → 反复「结束任务 / 开始接收任务」→ 执行顺序与下发顺序完全一致
    （不跳号、不重复），且**全程无波次在"未点开始接收"时被执行**
 ⑤ 重放被拦下的回滚必须是**放回队首**（重新开始接收仍先执行它，而不是跳到下一波）
 ⑥ 空队列 → PDQ_QUEUE_EMPTY，无动作
```
该测试直接 `#include "PendingWaveQueuePolicy.h"`（产品同一份判据）：**若有人把闸门改回去，
②④⑤ 立刻失败**。

## 五、影响面与兼容性

* **只改"何时出队"，不改"谁出队"**：队列仍是 FIFO，人工「切换选中波次」接管、H4 排队、H5 取消接替、
  「新任务」不消费队列等既有能力全部保留（`test/e2e_pending_replay.py`、`test/e2e_wave_isolation.py` 覆盖）。
* **不会再有"未点开始就自动开下一波"**：这正是现场要求；点「结束任务」后队列**只会保留**，
  在弹窗里可见（含冻结提示），点「开始接收任务」按队首顺序执行。
* **更安全**：修掉一处 `use-after-free`（悬垂引用）与一处"已下发波次被静默丢弃"，
  两者都会导致"波次数据对不上/凭空消失"。
* **不改数据库结构、不改协议报文**：H4/H6/H7/H8 报文口径与落库结构均未改动。
