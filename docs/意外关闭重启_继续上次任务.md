# 关闭切出波次 → 重启新任务 → 切回继续（关闭=切出+归档，开启=新任务无绑定）

> 版本：2026-09-15（★ 2026-09-16 更新：终态波次不再可切回；启动不再装载 XML 绑定）
> ★ 2026-09-17 更新（**口径更正 + 新增归属补齐**，见 `docs/格口绑定波次归属_根因与修复_20260917.md`）：
> - 现场实测发现三个缺陷，本文 §3.3/§3.4 的旧结论（"切回必然恢复绑定"）与事实不符，已更正：
>   ① **绑定行会整行丢失**（`order_code` NOT NULL，H6 到达时内存无波次 → 绑 NULL → 插入失败）；
>   ② **切出窗口会张冠李戴**（09-15 23:53 的 66 行 H6 实为 `456456` 的绑定，却记到 `6565656` 名下，
>      `456456` 切回时"无任何绑定可恢复"）；
>   ③ **切回取数"全有或全无"**（旧主口径要求"每格全表最后一条属本波次"，实测 14 个历史波次里 13 个返回 0 行；
>      部分命中时整体替换内存绑定 → 面板被清空）。
> - 修复：H4 到达时**归属补齐/纠偏**（只改 `order_code`、不增删行）；切回改以**本波次自己的记录**为主口径；
>   波次列表新增「格口绑定」列 + 「查看绑定」只读弹窗；绑定落库失败在界面红字告警。
>
> ★ 2026-09-17 现场口径变更（本轮）：**手动点「新任务」也清空格口绑定** ——
> 原实现是"绑定留用、等 WMS 新 H6 覆盖"，现改为与「关闭软件切出」「启动=新任务状态」同一口径：
> 逐格解绑留痕 → DB 归档（`active=0` + `unbind_time`，行与 `order_code` 永不改动）→ 内存清空
> （面板全部「未绑定」）→ 恢复满箱锁格格口。该波次的绑定记录因此仍在库里，**切回时逐格恢复**。
> ★ 关键取舍：只归档**已归属**的行（`order_code <> ''`），`order_code=''` 的"待补齐"行**保留 active** ——
> 否则 H4 到达时归属补齐不到它们，新波次又会 0 绑定（切回无绑定可恢复的老问题回归）。
> 详见 §一、"新任务"行 与 §五 第 1 条；回归用例见 `tests/test_restart_resume_db.cpp` ⑲。

> 需求（客户口径）：
> ① 每次关闭会切出该波次任务，保留所有信息以及格口绑定状态信息到数据库，便于回溯；
> ② 每次开启软件，自动开始新任务；新任务开始时需要清空格口绑定关系；
> ③ 需要继续上次任务时：从「波次数据记录」切回该波次 → 进度与格口绑定一并恢复。

> （`return_wave` / `return_wave_item` / `sorting_records` / `grid_box_bind` / `exception_record` / `outbox_*` / `wave_raw`），
> 因此**无需为保护切回而新增波次号标签**；逐项核对表见 `docs/波次归属与切回回溯_评估结论.md`。
> 历史重复落格明细（仅历史数据）可用只读脚本 `docs/dup_landing_report.py` 核对。

> **★ 2026-09-16 两处口径变更（现场需求）**：
> - **终态波次（已完成/已取消）不再允许切回**：不再提供"载入查看"模式；切回被拒时
>   **不切出当前波次、不动绑定**（守卫放在任何副作用之前）。失败 H7/H8 请用「重传」按钮补发。
>   详见 `docs/UI七项现场需求_切回限制与面板配色_20260916.md` 需求①。
> - **启动不再从 XML 装载绑定**：`config/http_server.xml` 的 `<binding>` 仅作历史镜像（只写不读）。
>   现场曾出现"开机后面板显示一堆历史箱号"，根因就是该 XML 残留被当作预绑定装载，现已修复。同上文档需求④。
>
> **★ 2026-09-16 断电路径核对与补齐（本次；现场情景见 §七）**：
> 情景 = 任务下发 → 格口容器全部绑定 → 点「开始分拣」（分拣中）→ **设备断电** →
> 次日开机（软件自启动 = 新任务状态）→ 在「波次数据记录」看到昨晚波次 → 切回继续分拣，
> 且**该波次绑定状态完好（该绑的已绑、未绑的还是未绑）**。核对结论与两处补齐：
> - **断电 = 异常关闭**：走不到 `closeEvent`/`switchOutWaveForExit()`，因此断电瞬间
>   `grid_box_bind` 的行仍是 `active=1`、波次状态仍是分拣中(3)；由**下次启动**的
>   `restoreWaveFromDB()` 兜底归档 → 开机必然是"新任务状态（面板全未绑定）"。
> - **补齐①（缺口：文档声称已做、代码未接线）**：切回时"已落格进度"重建
>   `HttpServer::restoreLandedProgress()`（原先 `getLandingRecordsForWave()` 定义在库里
>   却**无任何调用者**）→ 断电重启后继续分拣时，H7 报文含重启前已落的件、且不会突破每格口计划件数。
> - **补齐②**：H6 归属落空时绑定行不再整行丢失（`order_code` 绑 NULL 触发
>   `NOT NULL constraint failed` → 行根本没落库；现改为写空串保留该行）。
> - **已知边界（未改代码，见 §3.9）**：某格口在本波次内"满箱解绑/人工解绑"之后才断电，
>   切回会把该格当时那口满箱旧箱恢复为已绑 —— 与"未绑的还是未绑"不符；行数据无法区分
>   "满箱归档"与"关闭/启动归档"（都是 `active=0` + `unbind_time`），需客户确认口径后再动。

## 一、各动作的口径（一句话说清）

| 动作 | 行为 |
| --- | --- |
| **关闭软件** | **切出当前波次**：进度/明细/计划/落格/异常保留于 DB（状态保持原值，不改写）；**格口绑定归档**（`active=0` + `unbind_time` 留痕，逐格打 `[解绑留痕]`）；未成功的 H7/H8 保留在 outbox；内存全部清空 |
| **开启软件** | **新任务状态**：一律不装载任何绑定（面板全"未绑定"）——★ 2026-09-16 起**连 XML 里的 `<binding>` 预绑定也不再装载**（历史镜像，只写不读）；把 DB 中残留的 `active` 行全部归档；只打印提示"检测到未结束波次 X，可切回继续"；不自动装载任何进度 |
| **开始接收任务（按钮）** | ★ 2026-09-17 起与「新任务」同口径：`startReceive()` 在 `restoreWaveFromDB()`（清绑定+归档）之后调用 `resetWavePanelToIdle("开始接收任务")` —— 把当前内存波次**切出**（面板复位为"等待 WMS 下发新波次"），进度/明细/计划/落格/异常保留于 DB、可切回；待执行队列原样保留。无进行中波次时只记一条 INFO |
| **切回波次** | 绑定 + 波次状态 + SKU→格口映射 + 进度集合 + **已落格进度**全部按该波次从 DB 恢复，随后即可继续分拣；未成功 H7/H8 自动补发。**★ 2026-09-16 起：仅"未结束"波次可切回；已完成/已取消（终态）一律拒绝**，且拒绝时不切出当前波次。**★ 2026-09-17 起：绑定恢复以"该波次自己的记录（每格取本波次内最后一条）"为主口径**；本波次无任何绑定记录时，只按"物理当前绑定"显示并**明确告警"不是本波次的记录"**（见 §3.3） |
| **新任务（手动按钮）** | 语义 = "现在换下一波"：当前波次**切出**（进度/明细/计划/落格/异常保留于 DB，状态保持原值）＋**清空格口绑定**（逐格解绑留痕 → DB 归档 `active=0`+`unbind_time` → 内存清空，面板全部「未绑定」）＋ 恢复满箱锁格格口 ＋ 回到空闲等 WMS 下发新波次；待执行队列**原样保留**（不自动执行）。★ 2026-09-17 起由"绑定留用"改为"清空绑定"，与「关闭软件切出」「启动新任务状态」同口径；该波次绑定记录仍在库里，**切回时逐格恢复** |
| 异常关闭（崩溃/断电/强杀） | 走不到"关闭切出" → 由**下次启动**的 `restoreWaveFromDB()` 兜底归档；断电瞬间绑定行还是 `active=1`、波次状态保持原值，**任一时刻 DB 都处于"绑定已归档、波次可切回"的一致状态**。★ 2026-09-16：切回时按 DB 重建已落格进度（§3.8），断电重启后可无缝继续分拣 |

**关键设计**：`grid_box_bind` **只追加、不删除**，绑定每次变更都是"归档旧行 + 插入新行"。
所以"清空格口绑定关系"= 把 `active` 置 0（关系清了、界面未绑定），而**行与波次归属、绑定/解绑时间都还在** → 既能"新任务无绑定"，又能"切回恢复绑定"，还能"逐条回溯"。
切回时的取数口径 = **每格取该波次内最后一条绑定（容器号非空）**（`SQL_SELECT_LAST_BINDS_BY_ORDER` / `getBindsByOrder`，
见 §3.3 的口径更正）；
**刻意不看 `active`、也不看 `unbind_time`** —— 否则归档后就取不回绑定，两个需求会互相打架。

## 二、完整链路

```
① 关闭软件（窗口 X → 是）
     MainWindow::closeEvent → HttpServer::switchOutWaveForExit()
       · 逐格 [解绑留痕]（格口号/旧箱号/波次/原因=关闭软件切出波次）
       · archiveAllBinds()  → grid_box_bind 全部 active=0 + unbind_time
       · switchAwayCurrentWave() → 内存清空（SKU映射/格口记录/在途/分配表），DB 状态与进度保持原样
       · 内存绑定清空 → 面板回到"未绑定"
       · 打印可读摘要：[切出] 关闭软件：已切出波次 X（分拣中）——… 下次开启为新任务状态（未绑定）…
     随后 doActualStop()（停止接收 + 兜底落库）→ 设备/线程收尾

② 重新打开软件
     MainWindow::setupCore()  → **不装载任何绑定**（含 XML 里的 <binding>：历史镜像，只写不读）
                                面板初始即"全部未绑定"（灰底），等待 WMS 下发 H6
     MainWindow 开机自动执行一次「开始接收任务」
       → HttpServer::restoreWaveFromDB()
           · 内存绑定一律清空 → 界面显示"未绑定"（新任务状态）
           · DB 残留 active 行全部归档（只归档、不改归属；也不装载到界面）
           · 有未结束波次 → [容器绑定] 启动为新任务状态（全部格口未绑定）；检测到未结束波次 X（分拣中），
             明细 N 条 —— 进度与格口绑定已归档保留，可在「波次数据记录」切回继续
           · 无未结束波次 → 同样保持未绑定，等待 WMS 下发新波次

③ 切回（「波次数据记录」→ 选中该波次 → 点击「切换」→ resumeUnfinishedWave）
     · ★ 2026-09-16 入口守卫：已完成/已取消（终态）波次**直接拒绝**，不切出当前波次、不动绑定
     · 状态：分拣中→分拣中（直接继续）／已绑定→已绑定（等点「开始分拣」）／完结中→完结中
     · 映射与计划：从 return_wave_item 重建 SKU→格口 + 每格口计划 + 计划分配表
     · 进度：从 sorting_records / exception_record 重建已分拣、未闭环异常（同一件不会重复下发）
     · ★ 绑定：getBindsByOrder(该波次) → 非空则装载到内存与面板（**主口径，每格取本波次内最后一条**）
              （日志：切回波次恢复容器绑定 order=… count=N（来源=本波次的绑定记录；其中被更晚波次覆盖=K 个…））
              为空（该波次确实没有任何绑定记录）则按 DB 当前 active 绑定**仅显示**并明确告警；
              仍为空则保持未绑定 + 告警（等 WMS 下发 H6）
     · ★ 已落格进度：切回后用 sorting_records 补齐（下表）

④ 继续分拣：计划额度按真实已落数继续算；该格口满箱时 H7 报文包含重启前已落的件
```

## 三、实现要点（缺一不可）

### 3.1 关闭即切出 + 归档留痕（本次新增）

`HttpServer::switchOutWaveForExit()`（`MainWindow::closeEvent` 中、停止接收之前调用）：

- 先逐格留痕再清内存 —— 保证"归档的就是关掉那一刻的绑定映射"；
- `archiveAllBinds()` 失败时日志 ERROR + 界面红字，但**内存仍清空**（界面仍回到新任务状态），下次启动兜底重试；
- 切出**不改写波次状态**：`return_wave.status` 保持（分拣中/已绑定/完结中），切回时才能回到原来的阶段。

日志示例：

```
[解绑留痕] grid=001 旧箱=H-T0101 order=PP2026MOCK96990 原因=关闭软件切出波次 动作=DB归档(active=0)+内存清空
关闭切出波次 order=PP2026MOCK96990 status=3(分拣中) 绑定=3 归档=成功 H7待发=0 H8待发=1
[切出] 关闭软件：已切出波次 PP2026MOCK96990（分拣中）——进度/明细/计划/落格记录保留于数据库；格口绑定 3 个已归档留痕（归档成功）；未成功报文 满箱0 完结1 保留待补发；下次开启为新任务状态（未绑定），可从「波次数据记录」切回继续
```

### 3.2 启动=新任务状态（不再装载绑定）

`restoreWaveFromDB()`：启动只做①清空内存绑定（新任务状态）②归档 DB `active` 行（留痕）③提示未结束波次；
**不再**把 DB 绑定装载到界面。`MainWindow::setupCore()` 同步改为：XML 里的 `<binding>` 只在
"本次启动既无未结束波次、DB 也无 active 绑定"时作为兜底采用（现场手工预置用），否则忽略并日志说明。

日志示例：

```
启动为新任务状态（未绑定）：检测到未结束波次 order=PP2026MOCK96990 status=3(分拣中) items=12 DB active 绑定 3 个已归档保留 —— 切回该波次时随波次一起恢复
[容器绑定] 启动为新任务状态（全部格口未绑定）；检测到未结束波次 PP2026MOCK96990（分拣中，明细 12 条）——进度与格口绑定已归档保留于数据库，可在「波次数据记录」切回继续（切换时绑定与进度一并恢复）
```

### 3.3 切回时恢复该波次的绑定（★ 2026-09-17 口径更正：以"本波次自己的记录"为主口径）

`resumeUnfinishedWave()` 步骤 6 是恢复绑定的**唯一入口**，**只读不写库**。

> ★★ 2026-09-17 更正：旧实现的三级链把"每格**全表**最后一条属本波次"当主口径，
> 实测真实库 14 个历史波次里 13 个返回 **0 行**（该格口只要被更晚波次绑过就不再命中）；
> 而它一旦**部分命中**，旧实现就整体替换内存绑定（`loadContainerBindings` 是赋值不是合并）
> → 其余格口全变"未绑定"（现场"切回后面板被清空"）。
> 数学关系：`getBindsByOrderActive() ⊂ getBindsByOrder()`（"全表最后一条属本波次"
> ⇒ 该行必然也是"本波次内最后一条"）→ **先取后者绝不会漏格口**。

| 级别 | 来源 | 是否写库 | 命中场景 |
| --- | --- | --- | --- |
| **主口径** | `getBindsByOrder()`：每格取**本波次内**最后一条（箱号非空） | 否（本来就已存在） | 正常路径；**含已被更晚波次重新绑定**的格口 |
| 兜底 | `getAllActiveBinds()`（`active=1`，物理当前绑定） | **否（只显示）** | 本波次确实**没有任何**绑定记录（H6 归属从未落库 / 改造前旧库） |
| 全空 | 保持未绑定 + **明确告警** | 否 | 库中亦无活跃绑定 → 等 WMS 下发 H6（此时本也无法分拣） |

- `getBindsByOrderActive()` 保留但**降级为"确认口径"**：只用于统计"其中几个格口未被更晚波次覆盖"，
  写进日志标签（`来源=本波次的绑定记录；其中被更晚波次覆盖=K 个`），不再决定恢复哪个集合。
- 兜底一级只**显示**：日志与弹窗显式标注"**不是本波次的记录**"（避免被当成该波次的历史事实）。
- ★ **严禁用"每格历史上最后一次绑定"兜底**（曾这样实现，已彻底删除）：那会把历史旧箱全部复活绑到别的波次。
- ★ 2026-09-16 起：终态波次（已完成/已取消）**不允许切回**（入口守卫直接拒绝），
  因此本恢复流程只会对"未结束波次"执行；`isWaveTerminal()` 保留作防御性双保险。
- 恢复统一走 `applyWaveBinds()`，日志显式标注"仅显示不写库"，现场可核对来源。

```
切回波次恢复容器绑定 order=PP2026MOCK943 count=3（来源=本波次的绑定记录；其中被更晚波次覆盖=0 个；恢复前物理绑定=0 个）
恢复容器绑定(仅显示不写库) order=PP2026XXX count=32 来源=DB 当前活跃绑定（物理当前绑定，非本波次记录） 明细=001→H-A,002→H-B
[切换] 波次 PP2026XXX **没有任何绑定记录**（H6 归属落空/当时未绑定）——已按现场当前物理绑定显示 32 个（**不是本波次的记录**，仅显示不写库）；WMS 下发新 H6 时自动覆盖
```

### 3.4 ★★ 铁律：历史数据不得被粘贴进其它波次任务（格口绑定尤其如此）★★

**客户口径（2026-09-15 确认）**：历史数据不能被复制/粘贴进其它波次任务，格口绑定状态尤其如此。

由此确定三条硬约束（已落进代码）：

| 约束 | 落地 |
| --- | --- |
| **写入唯一来源 = H6** | 全仓库只有 H6 路由（`processRequest` 的 `BindingLatticePort` 分支）会调 `SortingDatabase::bindGridBox()`；切回/沿用/启动兜底三条路径**都不写库**（`HttpServer::applyWaveBinds()` 与 `restoreLandedProgress()` 只改内存与界面） |
| **不许有跨波次取数接口** | 已**删除** `getLastKnownBinds()`（每格历史上最后一次绑定）与 `getBindsWithEmptyOrder()`；跨波次取数一律走 `getAllActiveBinds()`（只反映"当前活跃"），且只用于显示 |
| **行归属不可改写** | `grid_box_bind.order_code` = 该次绑定**当时所属的波次**，是该行的永久归属：归档只改 `active/unbind_time`，`order_code` 永不改动、行永不删除、永不复制 |

因此：**每个波次的绑定行数只减不增**（只增 `active` 变化）——切换多少次、关闭重启多少轮都一样。

**现场根因修正（H6 早于 H4）**：run.log 实证 WMS 的 H6 常早于 H4 到达，那时内存波次为空 →
绑定行的 `order_code` 落空（该波次在库里确实"没有绑定记录"，这是事实，**不做任何复制**）。
解决方式是让**归属尽量不落空**，而不是事后复制：

- **切出窗口归属**：切出瞬间保留 `m_switchingOutOrderCode`（120s，`WAVE_SWITCH_OUT_KEEP_MS`），
  窗口内到达的 H6 记为刚切出的波次，并打 WARN 日志；
  ★ 2026-09-17：该窗口**确实救回过真实数据**（09-15 23:53 有 66 条 H6 靠它才落库），因此**保留**；
  但它同样会**张冠李戴** —— 同批 66 条 H6 实为下一个波次 `456456` 的绑定，却挂在 `6565656` 名下，
  于是 `456456` 切回时"无任何绑定可恢复"。处置 = **H4 到达时的归属纠偏**（见 §3.4.1），
  窗口机制本身不再扩大（`m_switchOutTime` 只用于界定"哪些行允许纠偏"）。
- **新任务状态下的 H6**：启动/新任务后内存波次为空，H6 仍会按"当次波次号"落库
  （WMS 下发 H4 后会重发 H6，见 run.log 的 `BindingLatticePort` → `InsertWaveInfo` 序列）；
  若确实落空则以 `order_code=''` 保留，H4 到达时由归属补齐改判（§3.4.1）。
- 归属确实落空的历史行不删除、不复制，仅作为"当前活跃绑定"在需要时**显示**，等 H6 覆盖。
  ★ 2026-09-16 修复：归属为空时 `order_code` 必须写**空串**而不是 NULL ——
  该列是 `NOT NULL`，绑 NULL 会让**整行插入失败**（历史 `data.log` 大量
  `NOT NULL constraint failed: grid_box_bind.order_code`），现场表现为"面板显示已绑定、库里一行都没有"；
  现在这类行会以 `order_code=''` 保留，可作"当前活跃绑定"查询与回溯（见 §3.9 第 5 条）。
  ★ 2026-09-17 补充：**该修复必须真的部署到现场 exe** —— 09-17 04:28 的 `data.log` 里仍有 93 条
  同款失败（报错行号 `<1596>` 对应修复前的二进制），波次 `789` 因此 0 行绑定、切回无绑定可恢复。
- ~~快照补记~~（**已于 2026-09-15 删除，勿再引用**）：早期实现曾用
  `recordWaveBindsSnapshot()` 把"当时内存里的绑定"补记成波次绑定行 ——
  这等于把历史复制进其它波次（现场出现"多绑一堆/65 个旧箱全部回绑"），已彻底移除。
  曾经打印过的日志（**现版本不会再出现**，仅供老日志比对）：
  `[绑定归位] grid=001 box=H-01-2001 order=… 来源=波次绑定快照补记 动作=重建绑定行`。

#### 3.4.1 ★ 2026-09-17 新增：H4 到达时的「归属补齐/纠偏」（唯一允许改写 `order_code` 的路径）

`onWavePersistenceFinished()`（H4 到达、本波次落库完成）→ `attributePendingBindsToWave(orderCode)`
→ `SortingDatabase::attributeBindsToWave(...)`，**在 `restoreBindsIfEmpty()` 之前**执行：

```sql
UPDATE grid_box_bind SET order_code = ?      -- 本波次
 WHERE active = 1                            -- 此刻物理生效
   AND bind_time >= ?                        -- 本次会话启动时刻：历史行永不改判
   AND (order_code = ''                      -- a) H6 早于 H4 → 空归属
        OR (order_code = ? AND order_code <> '' AND bind_time >= ?))  -- b) 切出窗口内的误归属
   AND grid_num NOT IN (SELECT grid_num FROM grid_box_bind WHERE order_code = ?)  -- 该格已有本波次记录则跳过
```

- 只改 `order_code`：**不新增/不删除行**（行数只可能不变），不动 `active/bind_time/unbind_time`；
- 现场含义：H6 早于 H4（波次 `789` 型）、切出窗口误归属（波次 `456456` 型）都能在 H4 到达时被补正，
  切回该波次即可恢复它自己的绑定；
- 审计：`data.log` 候选明细 + `http.log`/UI 日志
  `[绑定归属] 波次 W：已把 N 个格口的绑定补记到本波次（…）——仅补归属，未新增或删除任何绑定行`；
- 取舍（有意）：切出窗口内的行无法区分"A 的重发"与"即将下发的 B 的投递"，统一按后者处理
  （现场实测占绝对多数）；已归属其它波次、且不在窗口内的行**永不改判**。
  该取舍已被 `tests/test_restart_resume_db.cpp` 用例⑯ 锁定成断言。

### 3.5 「刷新绑定状态」不能把未结束任务的绑定当残留清掉（保持既有修复）

`checkContainerBindings()` 的归属判定参考波次 = 内存当前波次；内存无波次时取 DB 中未结束波次；
两者都没有才认定"任务已结束 → 绑定均为残留"。启动后（新任务状态）内存波次为空，
若参考波次不回退到 DB，点一次「刷新绑定状态」就会把绑定判为残留清理。

```
格口绑定归属校验 参考波次=PP2026MOCK96990（来源：数据库未结束波次（尚未切回））合计=3 保留=3 旧波次残留=0
```

### 3.6 切回时"已落格进度"必须补齐（★ 2026-09-16 接线完成）

重启后下列内存结构原本是空的，会在重启后的运行中暴露问题：

| 内存结构 | 空着的后果 |
| --- | --- |
| `m_gridSortRecords`（H7 满箱报文明细来源） | 该格口再满箱时"无分拣记录 跳过" ⇒ **箱内重启前已落的件永远不会上报** ⇒ WMS 数量对不上（整条驳回） |
| 计划额度（分配表 `landed` / `m_gridLandedNum`） | 已落件数被当成 0 ⇒ 重启后继续投件会**突破"每格口计划件数"上限**（且「计划分配表」的已落/余量与关闭前不一致） |
| 落格明细去重集合 | 同一件在换箱前后可能重复进 H7 明细 |

`SortingDatabase::getLandingRecordsForWave(orderCode)`（走线程独立只读连接，不挤占主写连接）
按落格先后正序返回该波次全部已落格明细（EPC/SKU/格口/容器号/库位/时间，含 `timeMs`），
切回时据此补齐三处，口径与实时落格路径逐条对齐：

- H7 明细分录：**只补"属于当前仍绑定容器"的件**（落格时固化的 `boxcode` == 当前绑定容器号）；
- 计划额度/封顶计数/落格去重：用**整波次全部落格**（跨容器累计，换箱不重置额度）。

> `getLandingRecordsForWave()` 当时只被单元测试调用，`resumeUnfinishedWave()` 里并没有重建动作

>
> ```
> 切回波次已落格进度重建 order=X 落格明细=12 行 额度/去重登记=12 行 H7明细补入=9 件[001:3件,048:6件] 跳过(旧容器=3 缺SKU=0 无绑定容器=0) —— 只重建内存与界面，未写库

### 3.8 断电路径（异常关闭）：开机与切回为什么必然一致

现场情景（§七）：**任务下发 → 格口容器全部绑定 → 点「开始分拣」（分拣中）→ 设备断电 → 次日开机 → 切回昨晚波次继续分拣**。

| 时刻 | 代码动作 | 数据库状态 | 界面 |
| --- | --- | --- | --- |
| 断电瞬间 | 进程消失（`closeEvent`/`switchOutWaveForExit()` **都不执行**） | `grid_box_bind` 的行仍是 `active=1`；`return_wave.status` 保持 3(分拣中)；已落格/异常/Outbox 早已逐条落库 | —— |
| 次日开机 | `MainWindow::setupCore()`：`loadContainerBindings({})` + 清 XML 镜像（**不读 XML**）；随后自动「开始接收任务」→ `startReceive()` → `restoreWaveFromDB()` | ① 内存绑定清空；② `getAllActiveBinds()` → `archiveAllBinds()`（`active=0` + `unbind_time`，**行与归属不动**）；③ 检出未结束波次并提示 | **全部格口"未绑定"（灰底）** |
| 看历史波次 | 「波次数据记录」`getAllWaves()` | 昨晚波次在列，状态 **分拣中(3)**；非终态 → 不标"（不可切回）"、切换按钮可用 | 可选中→切换 |
| 切回该波次 | `resumeUnfinishedWave()`：守卫(非终态)→校验→步骤3 映射/分配表→步骤4 进度集合→步骤5 `restoreWave`(状态回 3)→**步骤6 绑定**→**步骤7 已落格进度** | **只读**：三级兜底链取绑定、`getLandingRecordsForWave` 取落格明细；`resendOutbox` 补发未成功 H7/H8 | 该波次当时绑过的格口**逐格恢复**；没绑过的仍是未绑定 |

**绑定"逐格一致"的判定依据**（这就是"该绑的已绑、未绑的还是未绑"）：
`SQL_SELECT_BINDS_BY_ORDER_ACTIVE` 对**每个格口**取全表最后一条记录，且要求该记录
`order_code = 本波次`、`boxcode <> ''` —— 因此
· 本波次绑过的格口 → 命中该波次自己的行 → 恢复（含换箱后的最新箱）；
· 本波次**从未绑定**的格口 → 最后一条记录属于别的波次/归属为空 → **不返回** → 保持未绑定；
· 结果集**整体替换**内存绑定（`loadContainerBindings` 是赋值不是合并）→ 不会残留上一波次的绑定。

**断电与"正常关闭"的唯一差别**：断电时没有" 关闭切出"这一步，因此
① 断电瞬间库里是 `active=1`；② 归档由下次启动兜底完成。两者的**可切回结果完全一致**。

现场日志关键字（`log/HTTP/http.log`，`|` 分隔为可选）：

```
[容器绑定] 启动为新任务状态：不装载 XML 绑定（本次文件内 N 个已忽略）；未结束波次 1 个 / DB active 绑定 3 个…
启动为新任务状态（未绑定）：检测到未结束波次 order=X status=3(分拣中) items=N DB active 绑定 3 个已归档保留 —— 切回该波次时随波次一起恢复
[容器绑定] 启动为新任务状态（全部格口未绑定）；检测到未结束波次 X（分拣中，明细 N 条）——…
[解绑留痕] grid=001 旧箱=H-01-2001 order=X bindTime=… 原因=启动新任务状态（DB绑定归档）
启动归档 active 绑定 count=3 结果=成功（历史行保留，仅 active=0 + unbind_time 留痕；**不装载到界面** → 面板为新任务状态）

```

### 3.9 断电路径的已知边界（★ 需客户确认口径后才动代码）

1. **某格口在本波次内"满箱解绑/人工解绑"之后才断电** → 切回会把该格**当时那口满箱旧箱**恢复为已绑，
   与"未绑的还是未绑"不符。为什么取数口径区分不了：满箱解绑（`archiveGridBinds`）与关闭/启动归档
   （`archiveAllBinds`）在行上完全同形（都是 `active=0` + `unbind_time`），无法从行数据判定
   "这行是本波次在用、还是已被本波次主动解绑"。
   可选处置（**未实施**，需确认）：满箱解绑时追加一条"解绑留痕行"（`boxcode=''`）作为墓碑，
   取数时按 `boxcode <> ''` 自然排除；属**新增写入路径**，按现有铁律须先确认客户口径。
2. **同一波次内"同一箱号被复用"时，切回重建的 H7 明细可能把已上报过的件再算一次**：
   满箱 H7 成功后该格已解绑，若 WMS 又下发了**同一个箱号**（旧箱清空后继续用），
   崩溃/断电切回时按"落格时容器号 == 当前绑定容器号"过滤，会把上一轮该箱的件也补进明细。
   实时路径不受影响（满箱成功即 `m_gridSortRecords.remove(grid)` 清空 + 按新绑定重新记）。
   可选处置（**未实施**，需确认）：重建时再按 `outbox_fullbox` 中该 (波次,格口,箱号) 的
   **成功 H7 时间**过滤（`sort_time <= H7.createdAt` 的件判为已上报，不进明细、仍进额度）。
3. **在途（已下发、未收到落格反馈）不持久化**：断电重启后该件若再被 RFID 读到会重发一次 PLC 指令
   （不会重复计件：已分拣/落格去重/计划额度都在切回时按 DB 重建，见 §3.6）。
4. **H6 落库是异步的**（HTTP 已回 200 后入业务线程池写库）：若在"绑定刚下发、写库尚未落盘"的
   瞬间断电，该行可能不在库里 → 该格口切回时是未绑定（现场等 WMS 重发 H6 即可，不会错绑）。
5. **归属落空的 H6**（内存无波次、且不在切出窗口内，如开机后 WMS 先送 H6 后送 H4）：
   该行以 `order_code=''` 保留（只作"当前活跃绑定"可查，**不猜测归属**），
   **在 H4 到达时由归属补齐改判给该波次**（§3.4.1）—— 因此这类波次切回时能恢复出自己的绑定。
   ★ 2026-09-16 修复：此前该行会因 `order_code` 绑 NULL 触发
   `NOT NULL constraint failed` 而**整行插入失败**（现场表现为"面板显示已绑定、库里一行都没有"）。
   ★ 2026-09-17：该修复**必须重新编译部署 exe 才生效**（09-17 04:28 的现场日志证明当时跑的仍是旧二进制）。
6. ★ 2026-09-17 新增：**H6 报文本身不含波次号**，因此"报文自带波次号"是最彻底的解法 ——
   WCS 已支持 H6 可选带 `orderCode`/`order_code`/`waveCode`（query 或 JSON body），
   非空则**直接采用**、不再依赖任何推断；WMS 不改也能跑（缺省行为 = §3.4.1 的补齐/纠偏）。
7. ★ 2026-09-17 新增：**本波次已有该格记录时不改判** —— 极端情形下该格会保留本波次更早的那口箱
   （与内存当前箱可能不同）；`data.log` 会打出被跳过的候选行，可用「查看绑定」核对。

| ★★ 断电路径（本次新增，用例⑫） | 分拣中已绑定 → 断电（**不归档**，行仍 `active=1`）→ 开机兜底归档（面板全未绑定）→ 未结束波次可检出 → 切回**逐格一致**：该绑的已绑（含换箱后的当前箱）、未绑的仍未绑、不串其它波次；反复"断电→开机→切回"结果不变且绑定行数只减不增 |
| ★ 断电后继续分拣（本次新增，用例⑬） | 切回时按 `sorting_records` 重建：H7 明细**只补当前容器件**（旧箱件/无绑定格口不进）／计划额度按**整波次**累计（含旧箱件，重复行只算 1 件）／落格去重集合含全部落格件 |
| ★ H6 归属落空（本次新增，用例⑭） | 归属为空时绑定行以 `order_code=''` **保留**（不再因 NOT NULL 整行丢失）；不会被算进任何波次的绑定；开机兜底归档后不再活跃、行保留可回溯 |
| 进度输入 | 已落格明细 5 件（正序、含 SKU/容器号/库位/时间）／已分拣集合／未闭环异常／SKU→格口计划 |
| 旧箱件过滤 | 旧容器件保留原容器号（切回时按当前容器过滤，不重复上报） |
| 新波次 | 绑定 → 关闭切出 → 启动 → 切回即可恢复 |
| ★ 切换波次（现场关键） | A 绑定好 → 切到 B → 切回 A：绑定完整恢复；A↔B 来回多次仍各按自己的记录恢复；不串入对方绑定 |
| ★ 兜底链 | 格口被更晚波次覆盖 → ②本波次历史快照（只显示不写库）；本波次无绑定记录 → ③DB 当前活跃绑定（只显示不写库） |
| ★★ 历史不得粘贴进其它波次（铁律） | 切换多轮后各波次绑定行数**只减不增**；A/B 绑定互不掺入；从未绑定过的波次切回后仍为 0 行 |
| ★ 不得复活历史旧箱（现场回归） | 库里存有 65 个历史旧绑定（H-T0001..H-T0065）时，切回只恢复该波次自己的绑定，旧箱一个都不带 |
| ★ 写入唯一来源 = H6 | 切回/沿用/启动兜底三条路径都不产生新绑定行（WX 始终 0 行、WY 行数不变） |
| ★ 切出窗口 | 切出瞬间到达的 H6 归入刚切出的波次（不落到空波次） |
| ★ 快照补记（**已删除**） | 对应 `recordWaveBindsSnapshot()`，已因"跨波次复制绑定"移除；H6 归属改由切出窗口 + 空串归属保留处理（§3.4/§3.9） |

### 4.2 现场验证步骤（照做即可）

> 下面是**正常关闭**的步骤；**设备断电/强制结束进程（异常关闭）**的步骤、只读 SQL 与日志关键字见 §七。

1. 让该波次处于「分拣中」，格口绑定好（面板显示箱号）；
2. **直接关闭程序**（不要点「结束任务」）：确认弹窗说明会出现"当前波次将被切出保存…"；
3. 关闭时日志应出现：`[解绑留痕] grid=… 原因=关闭软件切出波次` 与
   `[切出] 关闭软件：已切出波次 X（分拣中）——…`；
4. 重新打开程序：绑定面板应**全部为"未绑定"（灰底）**（新任务状态），运行日志出现
   `[容器绑定] 启动为新任务状态：不装载 XML 绑定（本次文件内 N 个已忽略）…` 与
   `[容器绑定] 启动为新任务状态（全部格口未绑定）；检测到未结束波次 X…`；
5. 核对回溯数据（只读 SQL，见下）：该波次的绑定行仍在，已归档行 `active=0` 且 `unbind_time` 有值；
6. 「波次数据记录」→ 选中该波次 → 点击「切换」→ 确认后：
   - 绑定面板恢复为该波次的箱号；日志 `切换波次恢复容器绑定 order=… count=N（来源=本波次的归档绑定记录）`；
   - 波次状态回到原状态，已分拣/处理件数与关闭前一致；计划分配表「已落/余量」与关闭前一致；
   - ★ 若选中的是**已完成/已取消**的行：状态列会标注 `（不可切回）`、按钮变灰；
     强行双击/点击只会出现"不允许切回"日志，当前运行波次不受影响；
7. 继续上料分拣：已分拣过的件不会重复下发；该格口满箱时 H7 报文包含关闭前已落的件；
8. 若在切回之前点了「刷新绑定状态」：绑定不会被清掉（参考波次回退到 DB 未结束波次）。

现场只读核对 SQL：

```sql
-- 该波次的绑定状态（关闭后应全部 active=0 且 unbind_time 有值）
SELECT grid_num, boxcode, order_code, active, bind_time, unbind_time
  FROM grid_box_bind WHERE order_code = '<波次号>' ORDER BY grid_num, id;
-- 当前仍活跃的绑定（启动后应为空）
SELECT grid_num, boxcode, order_code FROM grid_box_bind WHERE active = 1;
```

## 五、已知边界（备忘）

- **手动「新任务」按钮**：★ 2026-09-17 口径变更 —— 现在**也清空格口绑定**（现场要求），
  与「关闭软件切出」「启动=新任务状态」同一口径：逐格解绑留痕 → `archiveAttributedBinds()`
  （只归档已归属行）→ 内存清空（面板全部「未绑定」）→ 恢复满箱锁格格口。
  该波次的绑定记录仍在库里（行与 `order_code` 永不改动）→ **切回时逐格恢复**。
  ★ 关键取舍：**只归档"已归属"的行**（`order_code <> ''`），`order_code=''` 的"待补齐"行
  **保留 `active`** —— 否则随后 H4 到达时归属补齐不到它们，新波次又会 0 绑定（切回无绑定可恢复的
  现场老问题回归）。回归用例：`tests/test_restart_resume_db.cpp` ⑲。
  （原先"绑定留用、等新 H6 覆盖"的做法已作废；与"软件启动=新任务状态"的差别仅在于
  启动用的是全量归档 `archiveAllBinds()` —— 那些行来自上一次会话，归属补齐的"本会话"时间护栏
  本来就不会认领它们。）
  入口有两处，都走 `HttpServer::startNewWaveTask()`：任务接收控制区的「新任务」按钮、
  「查看接收波次队列」弹窗里的「接收新任务」。
- **在途（已下发、未收到落格反馈）状态不持久化**：重启后该件若再被 RFID 读到，会重新下发一次 PLC 指令。
  不会重复计件 —— 落格明细去重集合、已分拣集合、计划额度都在切回时按 DB 重建。
- **历史库存在重复落格明细**（09-14 之前写入，仅历史数据）：切回时按 `(格口, EPC)` 与 `(格口, SKU, EPC)`
  两个键合并，不会重复计数；核对方式见 `docs/dup_landing_report.py`。
- **绑定历史表有界性**：每格每次换箱新增一行，长期运行行数随换箱次数增长；按波次/按格查询均为
  角标定位（每格最多命中一行，结果 ≤ 格口数 66），不影响性能；需要清历史时由 DBA 侧按需处理。
- **XML 里的 `<binding>` 预绑定**：程序在每次绑定变更后会把当前绑定写回 `http_server.xml`
  （既有行为，保留是为了不破坏落盘路径）。★ 2026-09-16 起 **只写不读**：启动时**任何情况都不装载**，
  且 `setupCore()` 会同步清空内存里的配置镜像（否则旧值会在随后的 `bindingUpdated` 保存里再写回）。
  绑定的唯一来源 = 本会话收到的 H6，或切回某个未结束波次时按其记录恢复。见 §3.8 与
  `docs/UI七项现场需求_切回限制与面板配色_20260916.md` 需求④。

## 七、断电路径现场验收（客户情景：断电 → 次日开机 → 切回继续）

**情景原文（客户口径）**：任务下发后，格口容器进行绑定；待全部绑定完后点「开始分拣」进入**分拣中**；
此时**设备断电**；第二天才开机，软件自启动后重新开始新任务；在**历史波次数据**里能看到昨晚波次的状态；
**切回昨晚的波次**后，依然可以继续该波次任务，且该波次下的**格口容器绑定状态完好**
（即**该绑的已绑，未绑的还是未绑**）。

### 7.1 验收步骤（照做即可，全程不需要改配置）

| 步骤 | 操作 | 期望 |
| --- | --- | --- |
| 1 | WMS 下发 H4 → 等格口绑定（H6）齐全 → 点「开始分拣」 | 面板显示各格口箱号；状态=分拣中；**记下面板上的箱号清单（用于第 6 步逐格对比）** |
| 2 | 投几件让该波次有"已落格"数据（可选，但建议；用于验证 H7 明细补齐） | 日志出现落格反馈；「计划分配表」该格口"已落"递增 |
| 3 | **直接断电/强制结束进程**（不要点关闭窗口、不要点「结束任务」） | 无 `[切出] 关闭软件…` 日志（这是与正常关闭的唯一差别） |
| 4 | 次日开机（软件自启动 = 新任务状态） | 面板**全部"未绑定"（灰底）**；日志见 §3.8 的"启动为新任务状态"与"归档 active 绑定"两条 |
| 5 | 打开「波次数据记录」，找到昨晚波次 | 状态列显示**分拣中**（非"（不可切回）"）；行可选中、切换按钮可用 |
| 6 | 选中该波次 → 点击「切换」→ 确认 | ① 绑定面板**逐格与第 1 步记录的清单一致**（该绑的已绑、未绑的还是未绑定）；② 状态回到分拣中；③ 日志出现 `切换波次恢复容器绑定 order=… count=N（来源=该波次的绑定记录）` 与 `切回波次已落格进度重建 …`；④ 「计划分配表」的已落/余量与断电前一致 |
| 7 | 继续上料分拣 | 已分拣过的件不会重复下发；该格口满箱时 **H7 报文包含断电前已落的件**（`Σqty` 与箱内实落一致）；继续投件不会突破每格口计划件数（超出者改投异常口 66） |

### 7.2 现场只读核对 SQL（按昨晚波次号替换 `'<波次号>'`）

```sql
-- ① 断电波次的头（状态应仍是 3=分拣中；异常关闭不改写状态）
SELECT order_code, order_qty, status, created_at, updated_at FROM return_wave WHERE order_code = '<波次号>';
-- ② 开机后应无 active 绑定（新任务状态）；行仍在、只被动过 active/unbind_time
SELECT grid_num, boxcode, order_code, active, bind_time, unbind_time
  FROM grid_box_bind WHERE active = 1;
-- ③ 该波次"当时绑过哪些格口"（切回后面板应与之一致：以下查询 = 切回取数口径）
SELECT g1.grid_num, g1.boxcode, g1.active, g1.bind_time, g1.unbind_time
  FROM grid_box_bind g1
 WHERE g1.order_code = '<波次号>' AND g1.boxcode <> ''
   AND g1.rowid = (SELECT MAX(g2.rowid) FROM grid_box_bind g2 WHERE g2.grid_num = g1.grid_num)
 ORDER BY CAST(g1.grid_num AS INTEGER);
-- ④ 该波次全部绑定行（含换箱前的旧行、含被更晚波次覆盖的行）= 逐条回溯
SELECT grid_num, boxcode, order_code, active, bind_time, unbind_time
  FROM grid_box_bind WHERE order_code = '<波次号>'
 ORDER BY CAST(grid_num AS INTEGER), id;
-- ⑤ 已落格明细（切回时重建 H7 明细/计划额度/去重的数据源；正序）
SELECT barcode, sku, grid_num, boxcode, volu, sort_time
  FROM sorting_records WHERE order_code = '<波次号>' AND barcode <> '' ORDER BY rowid;
-- ⑥ 归属落空但被保留的绑定行（2026-09-16 起不再整行丢失；不属任何波次）
SELECT grid_num, boxcode, active, bind_time, unbind_time
  FROM grid_box_bind WHERE order_code = '' ORDER BY id DESC LIMIT 20;
```
