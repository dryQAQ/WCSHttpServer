# 数据库表设计方案（ER 图版）

## 1. 概述

- **数据库引擎**：SQLite（本地嵌入式数据库，无需独立服务）
- **数据库文件**：`data/sorting_records.db`（位于 exe 同目录下）
- **连接方式**：Qt `QSqlDatabase` (`QSQLITE` 驱动)
- **性能模式**：WAL (Write-Ahead Logging)，支持读写并发
- **线程安全**：`QMutex` 保护所有数据库操作
- **配置宏**：`define.h` 中 `SORTING_DB_FILE` 定义文件路径

**PRAGMA 配置**：

| 指令 | 值 | 说明 |
|------|----|------|
| `journal_mode` | WAL | 允许读写并发，提升高并发场景性能 |
| `synchronous` | NORMAL | 安全性和写入性能之间取得平衡 |
| `cache_size` | 5000 | 约 20MB 缓存，减少磁盘 I/O |

## 7. 表结构详细说明

### 7.1 `sorting_records` — 分拣记录表

```mermaid
classDiagram
    class sorting_records {
        +int id PK "自增主键"
        +string order_code "波次号"
        +string barcode "条码"
        +string grid_num "格口号"
        +string car_num "小车号"
        +int grid_count "配货件数"
        +string volu "来源库位"
        +string sort_time "分拣时间"
        +string create_time "创建时间"
    }
    class idx_barcode {
        +string barcode
    }
    class idx_order_code {
        +string order_code
    }
    class idx_sort_time {
        +string sort_time
    }
    sorting_records --> idx_barcode : index
    sorting_records --> idx_order_code : index
    sorting_records --> idx_sort_time : index
```

**用途**：存储 PLC 落格反馈的每条分拣记录，用于 UI 查询展示和统计。

**索引**：

| 索引名 | 字段 | 用途 |
|--------|------|------|
| `idx_barcode` | `barcode` | 加速按条码查询历史 |
| `idx_order_code` | `order_code` | 加速按波次号查询 |
| `idx_sort_time` | `sort_time` | 加速按时间范围查询 |

**主要 SQL 操作**：

| 操作 | SQL 宏 | 说明 |
|------|--------|------|
| 插入 | `SQL_INSERT_RECORD` | PLC 落格反馈时写入 |
| 按条码查 | `SQL_QUERY_BY_BARCODE` | UI 条码查询，状态=已分拣 |
| 按时间查 | `SQL_QUERY_BY_TIME` | 按时间范围查询 |
| 按波次查 | `SQL_QUERY_BY_ORDER` | 按波次号查询 |
| 查全部 | `SQL_QUERY_ALL` | 查询所有记录 |
| 统计总数 | `SQL_COUNT_ALL` | 数据库总记录数 |
| 统计今日 | `SQL_COUNT_TODAY` | 当日记录数 |
| 清理过期 | `SQL_DELETE_OLD` | 删除 N 天前记录 |

### 7.2 `return_wave` — 退货波次头表

```mermaid
classDiagram
    class return_wave {
        +string order_code PK "波次号"
        +int order_qty "波次总件数"
        +int status "波次状态码"
        +string created_at "创建时间"
        +string updated_at "更新时间"
    }
```

**用途**：记录 WMS 下发的波次头信息，跟踪波次状态流转。

**波次状态枚举**（`WaveManager.h`）：

| 值 | 枚举名 | 中文 | 说明 |
|----|--------|------|------|
| 0 | `WAVE_IDLE` | 空闲 | 可接收新波次 |
| 1 | `WAVE_CREATED` | 已下发 | 波次下发成功落库 |
| 2 | `WAVE_BOUND` | 已绑定 | 至少一个业务格口完成有效容器绑定 |
| 3 | `WAVE_SORTING` | 分拣中 | 已开始分拣 |
| 4 | `WAVE_FULLBOX_SYNC` | 满箱同步中 | 正在调用/重试满箱回传 |
| 5 | `WAVE_CANCEL_PENDING` | 取消处理中 | 收到波次取消请求，判定中 |
| 6 | `WAVE_CANCELLED` | 已取消 | 波次取消成功（终态） |
| 7 | `WAVE_ENDING` | 完结中 | 正在调用/重试完结回传 |
| 8 | `WAVE_FINISHED` | 已完成 | 完结回传成功（终态） |
| 9 | `WAVE_HELD` | 异常挂起 | 接口失败/数据冲突，待人工处理 |

**SQL 操作**：

| 操作 | SQL 宏 | 说明 |
|------|--------|------|
| 插入/更新 | `SQL_UPSERT_RETURN_WAVE` | UPSERT，幂等覆盖 |
| 按波次查询 | `SQL_SELECT_WAVE_BY_ORDER` | 查询波次头信息 |
| 更新状态 | `SQL_UPDATE_WAVE_STATUS` | 状态变更时更新 |

### 7.3 `return_wave_item` — 退货波次明细表


**用途**：记录波次中每条商品→格口的分配明细，用于 UI 查询待分拣记录。

**格口类型**（`grid_type` 字段可选值）：

| 值 | 说明 |
|------|------|
| `普通格口` | 默认，常规分拣格口 |
| `专属发货格口` | 指定发货的专有格口 |
| `分类格口` | 按类别分配的格口 |
| `异常口` | 异常处理格口 |
| `混分格口` | 混合分拣格口 |

**SQL 操作**：

| 操作 | SQL 宏 | 说明 |
|------|--------|------|
| 批量插入 | `SQL_INSERT_WAVE_ITEM` | 事务内先删后插，支持覆盖重下 |
| 按波次查询 | `SQL_SELECT_WAVE_ITEMS` | 查询波次所有明细 |
| 增量分拣 | `SQL_INCREMENT_SORTED_QTY` | `sorted_qty + 1` |
| 查待分拣(按条码) | `SQL_QUERY_PENDING_BY_BARCODE` | 排除已落格（NOT EXISTS） |
| 查待分拣(按时间) | `SQL_QUERY_PENDING_BY_WAVE_TIME` | 按波次创建时间范围 |
| 查全部待分拣 | `SQL_QUERY_ALL_PENDING` | 留空查全部 |

## 9. 关键设计决策

### 9.1 为什么有两张分拣记录表（`sorting_records` + `sort_txn`）？

```mermaid
flowchart LR
    subgraph sorting_records["sorting_records(简化版)"]
        SR1["用于UI快速查询显示"]
        SR2["字段少, 查询快"]
        SR3["无唯一约束"]
    end
    subgraph sort_txn["sort_txn(完整版)"]
        ST1["用于精确分拣流水追溯"]
        ST2["带EPC防重"]
        ST3["order_code+epc UNIQUE"]
    end
    sorting_records --- sort_txn
```

### 9.2 为什么 NOT EXISTS 去重而不是 JOIN？

```sql
-- NOT EXISTS 方式（当前实现）✓
SELECT i.order_code, i.inco, i.grid_num, i.plan_qty, i.volu
FROM return_wave_item i
WHERE NOT EXISTS (
  SELECT 1 FROM sorting_records s
  WHERE s.barcode = i.inco AND s.order_code = i.order_code
)

-- VS LEFT JOIN 方式
SELECT i.* FROM return_wave_item i
LEFT JOIN sorting_records s ON s.barcode = i.inco AND s.order_code = i.order_code
WHERE s.id IS NULL
```

**选择 NOT EXISTS 的原因**：
- 语义更清晰：排除已落格 = 不存在于 sorting_records 中
- SQLite 优化器对 `NOT EXISTS` 与 `LEFT JOIN ... NULL` 的查询计划等价
- 避免 `LEFT JOIN` 可能产生的重复行

### 9.3 为什么 outbox 分为两张表？

```mermaid
flowchart LR
    FB["outbox_fullbox<br/>满箱回传<br/>需 boxcode 字段"] --> WMS
    END["outbox_end<br/>完结回传<br/>无需 boxcode 字段"] --> WMS
    WMS["WMS 系统"]
```

- 满箱回传（`outbox_fullbox`）需要 `boxcode` 字段（容器号），完结回传（`outbox_end`）不需要
- 两张表结构不同，拆分后避免大量空字段
- 独立的重试策略和调度逻辑

### 9.4 为什么所有时间字段用 TEXT？

SQLite 无原生 DATETIME 类型，TEXT 存储 ISO 8601 格式（`yyyy-MM-dd HH:mm:ss.zzz`）：
- 可读性好，直接查看数据库文件即可理解
- Qt 的 `QDateTime` 可以无缝转换
- 支持字符串比较操作（按字典序，与时间顺序一致）
